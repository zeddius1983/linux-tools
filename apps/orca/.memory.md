## orca

Orca (https://github.com/stablyai/orca, MIT): Stably AI's Electron desktop IDE for
running many coding agents (Claude Code, Codex, OpenCode, Copilot, ...) in
parallel, each in its own git worktree. Packaged from the official `.deb` of a
release picked in the wizard, in an `ubuntu:24.04` box, and exported to the host
menu. Added Oct 2026 at v1.4.245.

## Implementation

- `Dockerfile` — `FROM docker.io/ubuntu:24.04`. Extras: `curl`, `git`, `libpulse0`,
  Noto fonts, and `gh` from GitHub's APT repo (same block as `apps/opencode`).
  `ARG ORCA_RELEASE=latest` + `ARG CACHE_BUST`. `latest` is resolved to a tag
  through the `https://github.com/stablyai/orca/releases/latest` redirect
  (`curl -w '%{url_effective}'`, no API call), because the asset name carries
  the bare version: `releases/download/vX.Y.Z/orca-ide_X.Y.Z_<amd64|arm64>.deb`.
  A tag not starting `v<digit>` is refused, so a mobile tag fails early with a
  clear message instead of a 404.
- The `.deb` installs the app to `/opt/Orca/` (Electron binary `/opt/Orca/orca-ide`)
  and `/usr/share/applications/orca-ide.desktop` (`Exec=/opt/Orca/orca-ide %U`,
  `Icon=orca-ide`, `StartupWMClass=orca`). Its postinst symlinks
  `/usr/bin/orca-ide` → `/opt/Orca/resources/bin/orca-ide`, a bash shim that runs
  the bundled CLI with `ELECTRON_RUN_AS_NODE=1`. So the two `orca-ide`s differ:
  `/usr/bin/orca-ide` is the CLI, `/opt/Orca/orca-ide` the GUI.
- `exports` — `app:orca-ide:Orca` (package's own entry; content and basename
  both match `orca-ide`, so it lands at `orca-box-orca-ide.desktop`),
  `bin:orca-ide` (the CLI) and `bin:orca-tray`.
- **Tray icon** (`orca-tray`, GTK3 + AyatanaAppIndicator3, modelled on
  `apps/comfyui/comfyui-tray`). Exists because the terminal daemon outlives
  the window and Orca draws no tray icon on Linux. Shows window open/closed
  and the daemon's session count, with Open Orca and Quit Orca Completely…
  (confirm dialog, as Orca's own). The Dockerfile `sed`s the package entry's
  `Exec=/opt/Orca/orca-ide` to `/usr/bin/orca-ide-launch`, which `setsid`s the
  tray and `exec`s the GUI, so `app:` export stays. **The launcher's name must
  contain `orca-ide`**: `distrobox-export --app orca-ide` finds the entry by
  grepping `Exec=.*orca-ide.*` / `Name=.*orca-ide.*`, and `Name=` is `Orca`. It
  was first called `orca-launch`, and the export failed with `cannot find any
  desktop files`. The Dockerfile's `grep -q '^Exec=/usr/bin/orca-ide-launch '`
  checks the rewrite took. First launch after the rebuild (from a Cinnamon
  grouped-window-list pin, under a minute after the export) came up with
  no tray: Orca ran but `orca-ide-launch` never did. The pin names the right
  `orca-box-orca-ide.desktop`, and the same `distrobox-enter … orca-ide-launch`
  run by hand started the tray. Most likely Cinnamon launched from its cached
  copy of the entry (old `Exec=/opt/Orca/orca-ide`). Not reproduced. If the
  icon is missing, run `orca-tray` on the host. No `gui:` entry for the
  tray, as for comfyui. Single instance via `flock` on
  `~/.local/share/orca-tray/tray.lock`; the icon is staged into
  `~/.local/share/orca-tray/icons/` (the host's panel can't read `/usr`).
  It exits once no Orca process is left, after a 30 s startup grace.
  - Processes are matched by `/proc/<pid>/exe == /opt/Orca/orca-ide` **and**
    the tray's own mount namespace: with the host PID namespace a stale Orca
    from an old image is visible too. Main vs daemon vs helpers is decided on
    the whole cmdline: Chromium rewrites its children's argv into one
    space-joined string, so a per-arg `--type=` check counted zygotes and the
    GPU process as main processes.
  - Quit SIGTERMs the main process and the daemon, then SIGKILLs the rest of
    their process tree after 10 s. The main process alone isn't enough: a
    packaged Orca registers its SIGTERM-shuts-the-daemon handler only in dev
    builds (`let o=t&&!$.isServeMode`, `t` = isDev), so SIGTERM there is a
    plain quit. The daemon handles SIGTERM itself. No `orca` command on the host: that would shadow
  GNOME's Orca screen reader.
- The Dockerfile rewrites the entry's `MimeType=` to just `x-scheme-handler/orca;`,
  dropping `text/markdown`, `text/csv`, `text/tab-separated-values`.
- `wizard/00-release.buildarg` — `releases|stablyai/orca` plus
  `tag-match|^v[0-9]+\.[0-9]+\.[0-9]+$`. `tag-match|` was added to the wizard
  format for this app (`tui/releases.go` `fetchMatchingReleases`,
  `lib/wizard.sh` `_wizard_buildarg_values`): it fetches 100 releases and keeps
  the newest 10 that match.
- `icon.png` — the package's `hicolor/256x256/apps/orca-ide.png`.
- `category` = `Development`, with the other agent tools.

## Pitfalls and notes

- **The repo's release feed is two products.** `mobile-android-v0.0.N` Android
  pre-releases are interleaved with desktop `v1.4.N` releases, so a plain
  `releases|` page showed Android builds the Dockerfile can't install. Also,
  some `v*` git tags (e.g. v1.4.236, v1.4.234) have no published release, and
  there are `-rc.N` tags, so a `git ls-remote` items-cmd (codex's approach)
  would have offered uninstallable versions. Hence `releases|` + `tag-match|`.
  `/releases/latest` skips pre-releases, so it always resolves to a desktop tag.
- **In-app updater.** `resources/package-type` is `deb`, and for that Orca builds
  a `sudo apt install ./orca-ide_X.Y.Z_amd64.deb` command from the downloaded update
  (`ste()` in `out/main/index.js`) rather than replacing files. Inside the box
  that would upgrade only until the next `tools setup`. Left alone and
  documented. Making `package-type` unusable would disable it, but also makes
  the app report "updater-unavailable".
- **Profile is `~/.config/orca/`** (lowercase), not `~/.config/Orca/`.
- First launch, Linux Mint 22.3 X11, v1.4.244: window `orca.orca` "Orca",
  renders the onboarding flow with no extra GPU flags or `create_flags`.
  The log has the usual `system_bus_socket` D-Bus errors (no system bus in a
  box) and `login1.Manager.Inhibit` failing; both harmless. Onboarding flagged
  `gh` missing, which is why it was added.
- **Claude Code status line needs `jq` in the box** (added Oct 2026, v1.4.245).
  Orca's terminals are shells in `orca-box`, and a natively installed `claude`
  in the shared `~/.local/bin` runs right there, not in `claude-code-box`. So
  `~/.claude/statusline.sh` runs here too, and its single `jq` call failed with
  `jq: command not found`. Every field came back empty, and the script still
  drew a partial bar: the dir from `$PWD`, git from its own call, a `0/0 %`
  context segment and the clock. The model, in/out tokens, cache and 5h/7d
  segments disappeared. Any box whose terminal hosts agents needs whatever
  the shared dotfiles call.
- **The terminal daemon used to survive a rebuild.** Orca hosts its PTYs in a
  background `orca-ide .../daemon-entry.js` process (socket
  `~/.config/orca/daemon/daemon-v*.sock`, pid in `daemon-v*.pid`). Plain Quit
  and closing the window only *disconnect* from it; it is shut down only by
  **Quit Completely…** or a SIGTERM/SIGINT to the main process (the quit path
  picks `shutdownDaemon` vs `disconnectOnly` in `app.asar`). There is no tray
  icon on Linux, since Orca only creates one on win32/darwin.
  The whole app, not just the daemon, escapes the container's cgroup:
  Electron moves itself into `app-orca-<pid>.scope` over the shared session
  bus, so `distrobox rm --force` (which kills only `libpod-<id>.scope`) left
  it running on the deleted image, `podman ps` no longer listed it, and a
  relaunched Orca reconnected to the old daemon and kept opening terminals in
  the old box. Seen when adding `jq`: the new image had it, Orca's terminals
  didn't (`/run/.containerenv` `id=` was the old container, and Python there
  failed with `No module named 'encodings'`). Fixed generically by
  `stop_box_processes` in `lib/helpers.sh`, which `tools setup`/`tools rm` run
  before removing any box: it SIGTERMs (then SIGKILLs) every process whose
  `/proc/<pid>/root/run/.containerenv` names the box's container ID and whose
  cgroup is not the box's own. Orca's SIGTERM handler shuts the daemon down
  cleanly. This also kills a `tools setup orca` started from an Orca terminal;
  it runs first so that dies before anything is removed.
- `chrome-sandbox` is shipped `0755` and the postinst `chmod 4755`s it; it still
  works without SUID under rootless Podman (user namespaces), as for chatgpt.
- **distrobox-init's first-start packages are preinstalled** through the shared
  `lib/distrobox-deps` step, so it builds only through `tools`.
- Testing note: `pkill -f /opt/Orca/orca-ide` inside a compound shell command
  matches that shell's own command line and kills it; use `pkill -f '^/opt/Orca/orca-ide'`.
- **A stale dashboard binary ignores `tag-match|`.** `tools` builds
  `tui/tools-tui` only when it is missing, so in a working tree whose binary
  predates `tag-match|` the picker silently shows the Android pre-releases too
  (unknown page lines are skipped). Run `tools build-tui` after pulling Go
  changes. Release installs ship a binary CI built from the same tree.
