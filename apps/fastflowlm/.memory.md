## fastflowlm

FastFlowLM (FLM) — an Ollama-style LLM runtime that runs models entirely on the AMD
Ryzen™ AI NPU (XDNA2). Packaged as a container because only the *userspace* half of
the NPU stack (AMD XRT + the FLM binary) is containerizable; the `amdxdna` kernel
driver, NPU firmware, IOMMU and memlock limits are all host-side.

## Implementation

**Base image**: `docker.io/ubuntu:24.04`. The FLM release ships distro-specific
`.deb`s (debian13 / ubuntu24.04 / ubuntu25.10 / ubuntu26.04) — the 24.04 one is used
because its dependency set (`libavcodec60`, `libboost-program-options1.83.0`,
`libreadline8t64`, …) is exactly noble's.

**XRT from the lemonade PPA**: `ppa:lemonade-team/stable` is the only place with a
noble build of XRT 2.21.75, which is what the FLM `.deb` depends on
(`libxrt2 (>= 1:2.21.75), libxrt-npu2`). Installed packages: `libxrt2`,
`libxrt-npu2` (the amdxdna XRT plugin), `libxrt-utils-npu` (`xrt-smi`).
**Deliberately not installed: `amdxdna-dkms`** — that PPA package builds the *kernel*
driver, which a rootless container can neither build against the host kernel nor
load. The host supplies it (in-tree on 7.0+).

**Release selection**: `ARG FLM_REF=latest` resolves the download URL through the
GitHub releases API at build time, filtering assets for `*ubuntu24.04_amd64.deb`.
The `latest/download/<name>` shortcut is unusable here because the asset filename
embeds the version. `wizard/00-release.buildarg` offers the last 10 tags
interactively; `CACHE_BUST` (passed by `cmd_build`) forces the resolve+download layer
to re-run on every build.

**Exports**: the `.deb` already ships `/usr/bin/flm -> /opt/fastflowlm/bin/flm`, so
`bin:flm` works with no wrapper. `xrt-smi` is likewise already in `/usr/bin`.

**`flm-doctor`**: a `COPY`-ed script (build context is `apps/<name>/`, so a plain
`COPY flm-doctor` works) that checks every layer at once — kernel version, `amdxdna`
loaded, `/dev/accel/accel0` present + accessible, IOMMU state from `/proc/cmdline`
and `/sys/kernel/iommu_groups`, memlock rlimit, `xrt-smi examine`, `flm validate`.
It exists because the stack straddles the container boundary and a bare
"No NPU device found" from `flm validate` gives no clue which layer broke. It needs
no `distrobox-host-exec`: `/proc/cmdline`, `/sys/module/amdxdna` and
`/sys/kernel/iommu_groups` all reflect the *host* kernel from inside the container.

**`create_flags`**: `--device /dev/accel/accel0 --group-add 992 --security-opt
seccomp=unconfined --ipc=host`. No `--ulimit memlock` — see pitfalls.

## Pitfalls and notes

- **`amd_iommu=off` silently kills the NPU.** `amdxdna_drm_open()` binds the calling
  process's address space through IOMMU SVA. With the IOMMU disabled the driver still
  probes, the module still loads, and `/dev/accel/accel0` still exists — so every
  cheap check passes — but every `open()` fails with
  `[drm] *ERROR* amdxdna_drm_open: SVA bind device failed, ret -19`, surfacing as
  `xrt-smi: Open /dev/accel/accel0 failed (err=-19): No such device` and FLM's
  unhelpful `No NPU device found`. This was the state of the dev host when the app was
  written (its cmdline also carries `amdgpu.gttsize=` / `ttm.pages_limit=` Strix Halo
  VRAM tuning, which is presumably why the IOMMU was turned off). `flm-doctor` checks
  `/proc/cmdline` explicitly for this reason — it is not something the container can
  fix.
- **Do not put `--ulimit memlock=-1:-1` in `create_flags`.** Rootless Podman cannot
  raise a limit above the host user's *hard* limit, so on a host where
  `ulimit -Hl` is finite (Mint/Ubuntu default ≈ 15.6 GB) the container fails to start
  instead of getting unlimited memlock. Raising it for real requires editing
  `/etc/security/limits.conf` on the host and rebooting; `flm-doctor` reports the
  current value and prints the fix rather than attempting it.
- **The device must exist before `tools create`.** `--device /dev/accel/accel0` is
  resolved by Podman at container-create time; on a host without the NPU exposed,
  creation fails outright rather than degrading.
- **`--group-add 992` is the host's `render` GID**, matching `lmstudio` /
  `llama-cpp-rocm`. Distrobox already passes
  `--annotation run.oci.keep_original_groups=1`, so host supplementary groups carry
  through regardless; the explicit GID is belt-and-braces and consistent with the
  other GPU apps. Per the repo-wide rule, it is numeric — Ubuntu images have no
  `render` group name for Podman to resolve.
- **`flm validate` and `flm run` disagree.** Validate reads the DRM device directly;
  `run` goes through `xrt::device(0)`. A passing validate with a failing run means XRT
  cannot see the device — check `libxrt-npu2` is installed and `xrt-smi examine`
  lists an NPU.
- **XDNA1 is not supported.** Ryzen AI 7000/8000/200-series will never work with FLM
  regardless of driver state.
- `flm serve` binds port 52625; distrobox's host networking makes it reachable from
  the host with no extra flags.
