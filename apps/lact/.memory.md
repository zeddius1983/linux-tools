## lact

[LACT](https://github.com/ilya-zlobintsev/LACT) — Linux GPU Control Application:
GTK4 GUI plus a system daemon for AMD/NVIDIA/Intel GPU power caps, fan curves,
clock and voltage offsets, power states and per-process settings profiles.

Packaged for the release picker and the one-command install/uninstall, not for
containerisation — see below.

## Implementation

**Host-only, with `install.sh` — not a container.** The app joins
`nvidia-cdi-service` and `nvidia-acs-service` in the `host-only` + `install.sh`
category (`is_hostonly_installer` in `lib/helpers.sh` requires the marker **and**
`install.sh` **and** no Dockerfile).

`lactd` runs as root writing GPU control files under `/sys/class/drm/*/device/`,
which rootless Podman cannot do with any amount of `--privileged` — the wall
`corefreq` hits with `insmod`. But that argument alone is **not** sufficient, and
it was the only one given on the first pass: it justifies the *daemon* living on
the host, not the whole app being host-only. `corefreq` puts its daemon on the
host too and still ships a container for the client. The real reasons the same
split is wrong here, checked rather than assumed:

1. **A container would add an install step, not remove one.** This is the actual
   difference from `corefreq`, whose container earns its place by *building* a
   kernel module against the host kernel — a hard host dependency the container
   eliminates, leaving the host only to `insmod` the result. LACT's daemon is a
   distro package plus a systemd unit; no container removes that host install, so
   a containerised GUI means installing on the host *and* building a box.
2. **The GUI has no host dependency worth escaping.** It needs GTK4, and upstream
   already requires Debian 12+ / Ubuntu 22.04+ *because* older releases lack
   GTK4. Every host LACT supports already has what the GUI needs.
3. **Every socket-bridging route is worse than it looks.** The client's socket
   path is hardcoded in `get_socket_path()` (`lact-client/src/lib.rs`):
   `/run/lactd.sock`, falling back to `/run/user/<uid>/lactd.sock`. No env var,
   no client-side config. That leaves three options, all bad:
   - Bind-mounting `/run/lactd.sock` through `create_flags` binds an **inode**.
     `sudo systemctl restart lactd` — which upstream's own docs prescribe after
     changing `log_level` or permissions — unlinks and recreates the socket, so
     the mount is left pointing at a deleted inode and the GUI cannot reconnect
     until the box is recreated. The most attractive-looking route fails on a
     documented routine operation.
   - Symlinking to `/run/host/run/lactd.sock` (Distrobox does expose the host
     root there, verified) relies on image-time content under `/run`, which a
     runtime tmpfs is liable to wipe.
   - The `tcp_listen_address` listener does work — Distrobox shares the host
     network namespace, verified: a box sees the host's real interfaces, so
     `127.0.0.1:12853` is the host's loopback. But it is unauthenticated and
     unencrypted root-level GPU control, which upstream ships disabled behind an
     explicit warning. Not worth trading for a container.

Upstream's own container image
([docs/DOCKER.md](https://github.com/ilya-zlobintsev/LACT/blob/master/docs/DOCKER.md))
is daemon+CLI with **no GUI**, and documents rootful Docker with
`--privileged -v /dev/dri:/dev/dri` — consistent with all of the above.

**Core change this app required: `.buildarg` answers now reach host-only
installers.** A `.buildarg` page's value is consumed by `cmd_build` as
`--build-arg`. A host-only app never builds an image, so a version picker on one
would have been collected by the wizard and then silently thrown away. `cmd_setup`'s
host-only branch now converts `wizard_build_args` output into environment
assignments and runs `install.sh` under `env`. `install.sh` reads
`LACT_VERSION`, defaulting to `latest`. This generalises: any future host-only
app gets wizard answers the same way.

**Release picker uses `items-cmd` + `notes-repo`, not `releases|`.** Two reasons,
both discovered from the live API:

1. The API returns the rolling `test-build` prerelease **first**, so a plain
   `releases|ilya-zlobintsev/LACT` page would default to a dev build — a poor
   default for something that writes voltage curves. The `items-cmd` filters to
   `v[0-9]*` tags in API order, so the default is the newest *stable* release.
2. `test-build` is still worth offering (upstream documents it as the way to get
   unreleased fixes), so it is appended inside the `items-cmd` itself.

`notes-repo|ilya-zlobintsev/LACT` then attaches each tag's changelog and date, so
the picker shows release notes exactly as a `releases|` page would.

**Asset resolution is done from the release's asset list, never by building a
filename.** Upstream ships one package per distro release, and the installer
walks a priority list of name fragments from `/etc/os-release`.

## Pitfalls and notes

- **`extra|` does nothing on an `items-cmd` page.** It is only read on the
  `releases|` path (`buildArgItems` in `tui/wizardui.go` appends `p.Extra` inside
  the `ReleasesRepo` branch and returns before the items-cmd path). A page that
  writes `extra|test-build` next to an `items-cmd` gets no error and no extra
  entry — the line is silently ignored. That cost a debugging round here; the
  fix is the established idiom of folding the literal into the command itself,
  the way `openclaw` and `codex-cli` prepend `latest`.

- **The Arch asset is `...pkg.tar.arch.zst`, and `*.pkg.tar.zst` does not match
  it.** Upstream inserts `.arch` between `.tar` and `.zst` to tell that build
  apart from the others in the same release, so a conventional pacman glob
  misses it and the file falls through to "don't know how to install". This is
  how the first CachyOS install failed — after downloading the right package.
  The case now also matches `*.pkg.tar.*.zst`, and the file is renamed to the
  conventional `...pkg.tar.zst` before `pacman -U` rather than trusting pacman
  to accept an extension it never produces. The contents are an ordinary zstd
  package (`.PKGINFO`, `.MTREE`, `.BUILDINFO`, `usr/bin/lact`) — only the name
  is unusual.

  Lesson that generalises past this app: verifying that the *right asset is
  selected* is not the same as verifying it *installs*. Asset resolution was
  tested against the live API for three tags and looked complete, while the
  install command for one of the three formats had never been exercised at all.

- **Arch derivatives need an `ID_LIKE` fallback, not just an ID list.** The
  first version matched `arch|cachyos|endeavouros|manjaro` by `ID` alone, so
  anything else Arch-based (Garuda, and whatever ships next) would have fallen
  through to "no LACT package matches this host". `ID_LIKE=*arch*` now catches
  them. Verified with injected os-release values for cachyos, arch, garuda and
  endeavouros.

- **Every release ships a `lact-headless-*` twin for each distro target.** A
  naive `grep ubuntu-2404.deb` matches both, and picking the headless build
  installs a daemon with no GUI — a failure that looks like "the GUI package is
  broken" rather than "wrong package". The matcher excludes names beginning
  `lact-headless-`.

- **`test-build`'s assets are not named after its tag.** It is rebuilt from the
  latest commit continuously and carries whatever version it was built from
  (`lact-0.10.1-*` at the time of writing), while GitHub shows it with a 2023
  date. Any code that constructs a download URL from the tag breaks on it. This
  is why the installer reads `browser_download_url` from the release JSON —
  verified against `latest`, a pinned `v0.9.1`, and `test-build`, all three of
  which resolve correctly.

- **Ubuntu derivatives need `UBUNTU_CODENAME`, not `VERSION_ID`.** Mint 22.3
  reports `ID=linuxmint`, `VERSION_ID=22.3`, `UBUNTU_CODENAME=noble`. Its own
  version number means nothing to LACT's asset names; the codename is what maps
  to `ubuntu-2404.deb`. The same applies to Pop!_OS and elementary.

- **Do not `source install.sh` to test its functions.** The dispatcher at the
  bottom runs on source, which during development here started a real install
  (it got as far as `sudo apt-get install` before failing for want of a TTY).
  Extract the function with `sed -n '/^name()/,/^}/p'` and source that instead.

- **An `EXIT` trap referencing a `local` variable fails under `set -u`, and it
  fails *after* the work succeeded.** The first version did
  `local tmp; tmp="$(mktemp -d)"; trap 'rm -rf "$tmp"' EXIT` inside `install()`.
  The trap body is single-quoted, so `$tmp` expands when the trap fires — at
  script exit, by which point `install()` has returned and its `local` is out of
  scope. Result: `line 1: tmp: unbound variable`, a non-zero exit, and
  `Error: install.sh failed for 'lact'` — on a run that had already installed
  the package and started the daemon successfully. The temp dir also leaked,
  since `rm` never ran. Fixed with a global `WORKDIR` and a `cleanup()` function
  trapped once at the top of the script. Worth remembering for every installer
  here: a misleading failure at the end is worse than an honest one at the start,
  because it invites undoing work that actually succeeded.

- **`mktemp -d` is 0700, which apt cannot read.** apt drops to the `_apt` user
  to download and cannot traverse the directory, so it prints
  `Download is performed unsandboxed as root as file '...' couldn't be accessed
  by user '_apt'` and falls back to fetching as root. Harmless — the file is a
  public release artifact — but avoidable with `chmod 0755` on the scratch dir.

- **Verified on Linux Mint 22.3**: the `ubuntu-2404.deb` asset installed LACT
  0.10.1, `lactd` enabled and active, `/etc/lact/config.yaml` created. The sudo
  half is therefore no longer unverified; the CachyOS badge stays grey.

- **AMD overclocking needs `amdgpu.ppfeaturemask=0xffffffff`** on the kernel
  command line, or the controls are present but inert. LACT's GUI can write the
  bootloader change itself. Worth knowing before concluding the app is broken on
  an AMD card.
