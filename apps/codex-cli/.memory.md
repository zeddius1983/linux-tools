## codex-cli

Packages OpenAI Codex CLI in an Ubuntu 24.04 Distrobox and exports `codex` as a
host binary plus a terminal desktop launcher. Git, GitHub CLI, and Bubblewrap
are included for common coding-agent workflows.

## Implementation

- Installs the prebuilt Rust CLI with OpenAI's standalone installer at image
  build time (`https://chatgpt.com/codex/install.sh`).
- `wizard/00-release.buildarg` is a single-choice release picker for `setup`
  and `build`. It emits `latest` first (the default), followed by the ten newest
  stable `rust-vX.Y.Z` tags from `openai/codex`, and passes the selected value as
  Docker build arg `CODEX_RELEASE`.
- Non-interactive builds use `ARG CODEX_RELEASE=latest`, matching OpenAI's
  documented install/update command.
- The installer runs with temporary `HOME=/opt/codex-install`, persistent
  `CODEX_HOME=/opt/codex`, and `CODEX_INSTALL_DIR=/usr/bin`. This leaves the
  exported command at a path `command -pv` can find while preserving the
  installer's complete release tree (including bundled `rg` and Bubblewrap
  resources) under `/opt/codex`. Only the temporary home is removed.
- `ARG CACHE_BUST` is declared immediately before the installer layer.
  `cmd_build` supplies a fresh epoch value on every build, forcing the selected
  release to be resolved and downloaded again while retaining cache for the
  OS and GitHub CLI package layers.

- **Optional status line** (`wizard/01-statusline.packages` + `codex-cli-install`):
  sets `tui.status_line` in `~/.codex/config.toml`, opt-in via the setup wizard.
  - Reuses the existing `.packages` wizard type (like `claude-code` and
    `dev-toolbox`) — **no `lib/` changes**. The wizard runs
    `codex-cli-install --tools "statusline"` inside the box; because `$HOME` is
    shared, it writes to the host's `~/.codex/`.
  - Items written: `project-name git-branch pull-request-number model
    context-used five-hour-limit weekly-limit` — the closest built-in equivalent
    to this repo's Claude Code status line.
  - Numbered `01-` so the release picker (`00-release.buildarg`) still runs first;
    `tui_run_wizards` walks the pages in glob order.
- `python3` + `python3-tomlkit` are installed for `codex-cli-install`. tomlkit
  round-trips comments and formatting, which matters because `config.toml` is a
  file the user hand-edits. `python3` came in transitively before this change but
  is now listed explicitly, since the installer depends on it directly.

## Pitfalls and notes

- Removing the named image is not sufficient to refresh an unchanged build
  layer. Before `CACHE_BUST` was consumed by this Dockerfile, repeated
  `tools setup codex-cli` runs could reuse the old standalone-installer result;
  this produced an older CLI that immediately advertised a newer release.
- `CODEX_RELEASE` must be present in the environment of the shell executing
  the downloaded installer. Assigning it only to `curl` on the left side of a
  pipe does not pass it to `sh`, so the Dockerfile downloads the script first
  and then invokes it with the variable explicitly set.
- Do not copy only the `codex` ELF out of the standalone installation and then
  delete its release directory. Current package releases also carry resources
  such as `codex-path/rg` and `codex-resources/bwrap`; keeping the installer's
  `/opt/codex/packages/standalone` layout preserves those relative assets.
- The upstream installer accepts `latest`, `X.Y.Z`, `vX.Y.Z`, or
  `rust-vX.Y.Z`. The wizard strips the `rust-v` tag prefix and excludes alpha
  and beta tags so its pinned choices are stable versions accepted verbatim.
- Runtime self-update is not the packaging path. `/usr/bin/codex` is owned by
  the image, and the host export always enters the box to execute that binary.
  Re-run `tools setup codex-cli` to update or change versions; shared
  `~/.codex/` state survives the rebuild.

- **Codex cannot run a custom status-line command — this is not a packaging
  limitation, it is the feature's shape.** `tui.status_line` is typed
  `array<string> | null`: an ordered list of *built-in* item identifiers. There is
  no hook to execute a script and render its stdout, so `apps/claude-code/statusline.sh`
  has nothing to attach to and cannot be reused or adapted. Codex draws the bar
  itself, joining items with a hardcoded `" · "` separator (`STATUS_LINE_SEPARATOR`)
  and coloring them via a fixed accent map (model→cyan, path→green, branch→magenta,
  `fallback_style()`), derived from its own theme. **The Codex bar will never
  visually match the Claude Code one**; only the information content can be
  aligned. **Re-confirmed against the 0.153.4 binary**, not just the docs: the
  identifier enum has no `custom`/`text`/`command`/format-string variant, and the
  `[tui]` struct's only status-line fields are `status_line` and the boolean
  `status_line_use_colors` — so Nerd Font glyphs and powerline separators are out
  too, not just custom commands. Expect to be asked "can we make it look like the
  Claude Code one" more than once; re-verify with the two greps below rather than
  re-reading upstream, it takes about a minute.
- **The canonical item identifiers live in
  `codex-rs/tui/src/bottom_pane/status_line_setup.rs`**, as a strum enum with
  `serialize_all = "kebab_case"` plus per-variant `to_string`/`serialize`
  overrides — so the accepted spelling is not always the obvious kebab-case of the
  variant name. Notably `ModelName` → `model` (not `model-name`), `ProjectRoot` →
  `project-name` (aliases: `project`, `project-root`), `Status` → `run-state`
  (alias `status`), `ContextUsed` → `context-used` (legacy alias `context-usage`),
  `SessionId` → `thread-id` (alias `session-id`). Verify against that file rather
  than guessing; the published config reference lists the key but not the full
  item set.
- **The full item set can be recovered from the binary offline** — faster and more
  reliable than chasing the source. The variants are laid down as one contiguous
  run of strings, so `strings -n 4 codex | grep -a context-remaining` prints the
  whole enum in one line. Extract the binary first (it is at
  `/opt/codex/packages/standalone/releases/<ver>-x86_64-unknown-linux-musl/bin/codex`,
  and the image has no `strings`, so `podman cp` it out). Verified complete set as
  of **0.153.4**:

  ```
  project-name  current-dir  status  run-state  thread-title  git-branch
  context-remaining  context-used  context-window-size  five-hour-limit
  weekly-limit  thread-credits  estimated-thread-cost  codex-version
  used-tokens  total-input-tokens  total-output-tokens  thread-id
  fast-mode  model  model-with-reasoning  reasoning  task-progress
  pull-request-number  branch-changes  permissions  approval-mode
  raw-output  workspace-headline
  ```

  To spot-check a single name, `grep -qa -- <item> <binary>` works too — always
  grep a name you know is bogus as a control. Prefer this over both the source-tree
  lookup above and anything that starts a session.
- **Dump the whole `[tui]` struct** — the field names are also one contiguous run:
  `strings -n 4 codex | grep -ao 'raw_output_modestatus_line[a-z_]*'`. This is what
  establishes that `status_line_use_colors` is the *only* styling knob.
- **`[tui].terminal_title` consumes the same identifier set** (the binary carries a
  matching "terminal title configuration contains unknown item identifiers"
  diagnostic). Worth knowing before assuming these identifiers are status-line-only.
- **`.tmTheme` files under `$CODEX_HOME/themes/` are syntax highlighting, not the
  status bar.** The strings around that code path belong to the `two-face` crate
  and name TextMate scopes (`entity.name.type`, `keyword.operator`), so a custom
  theme there is not a route to recoloring the status line. Not tested further —
  do not assume either way without checking.
- **Don't probe config validity by running `codex exec`.** `--help` short-circuits
  before config parsing, so a bad `-c` override there produces no error — and
  `codex exec "..."` *does* parse config but also starts a real billed session
  against the user's account. An invalid identifier is not rejected in `exec` at
  all (no TUI renders), so it proves nothing either way. Validate item names
  against the source enum instead.
- **Wizard detection is file-existence only and cannot inspect a TOML key.**
  `_wizard_run_page`/`_wizard_apply_packages` in `lib/wizard.sh` only test paths
  (`~/…` or `~/.local/bin/<name>`), so there is no way to detect "is
  `tui.status_line` set" directly. Hence the marker at
  `~/.codex/.linux-tools-statusline`, which doubles as a record of exactly which
  items we wrote — that record is what makes a safe toggle-off possible (revert
  only if the current list still matches ours, otherwise leave the user's
  customisation alone).
- **`config.toml` edits must preserve comments.** Unlike `claude-code`'s
  `settings.json`, which `jq` can safely rewrite, this is TOML that users hand-edit
  and comment. `tomlkit` (not `tomllib`, which is read-only, nor `toml`, which
  discards comments) is the reason `python3-tomlkit` is in the image. The installer
  refuses to write at all if the file exists but doesn't parse, so a hand-edited
  config is never clobbered.
- **Removing `tui.status_line` must not delete a `[tui]` table the user is using.**
  The uninstall path deletes the key, then drops the `[tui]` table *only* if it is
  empty afterwards — a config with `[tui] theme = "dark"` keeps both the table and
  the theme.
