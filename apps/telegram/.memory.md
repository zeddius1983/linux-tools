## telegram

Telegram Desktop, the official client, from the `telegram.org` Linux tarball in
an `ubuntu:24.04` box (pinned to `linux/amd64`, since the tarball is x86-64 only).
Exported as a `gui:` launcher.

## Implementation

- **Base image**: `FROM --platform=linux/amd64 ubuntu:24.04`. Still unqualified,
  grandfathered in `scripts/lint-apps.sh` `LEGACY_UNQUALIFIED_FROM`.
- **Install**: `curl https://telegram.org/dl/desktop/linux` (always the current
  release) → `/opt/Telegram`. `/usr/bin/telegram-desktop` is a wrapper script
  (`apps/telegram/telegram-desktop`, was a symlink until Oct 2026) that `exec`s
  `/opt/Telegram/Telegram` with `DESKTOPINTEGRATION=1` and the private
  `XDG_CURRENT_DESKTOP` prefix (see the link handling below), after setting up
  the host's link handler; it's in `/usr/bin` so `command -pv` finds it.
- **Dependencies**: the Qt XCB platform libraries (`libxcb-*`,
  `libxkbcommon-x11-0`, …), `libfontconfig1`, and the Mesa GL/EGL stack;
  `mesa-utils` + `vulkan-tools` for diagnosis.
- **Exports**: `gui:telegram-desktop:Telegram` (`Terminal=false` desktop entry
  running `distrobox enter telegram-box -- /bin/telegram-desktop`), and
  `bin:telegram-desktop`, which the link handler's Exec relies on (see below).
- **README.md** added in Oct 2026 (it was missing, so the dashboard info panel was
  empty).

## Pitfalls and notes

- **Telegram writes its own desktop entry on the host, on every start (fixed).**
  With `$HOME` shared, `~/.local/share/applications/org.telegram.desktop._<hash>.desktop`
  appeared with `Exec=/opt/Telegram/Telegram -- %U`, a path that only exists in
  the box, so the host menu had a broken duplicate "Telegram". Verified it's
  rewritten within ~1s of every launch, so deleting it once never helped.
  Fix: the env var `DESKTOPINTEGRATION` (found with `grep -a` in the binary; any
  non-empty value) makes Telegram skip writing it. Verified: with it set, nothing
  was written in 30s of running. The wrapper also deletes a stale copy whose
  `Exec` points into `/opt/Telegram`, so existing hosts clean themselves up on the
  next launch. Telegram's hicolor icons in `~/.local/share/icons` are left alone:
  they're harmless and named by icon-theme id, not by path. The `/etc/tdesktop/externalupdater`
  mechanism, which would also have disabled it, isn't in this build (no such
  string in the binary).
- **URL scheme handlers (fixed Oct 2026).** Telegram registers `tg://`,
  `ton://` and `tonsite://` through GIO on every start unless the *current default
  handler's command line* is exactly its own, `/opt/Telegram/Telegram -- %u`. When
  it isn't, it creates `userapp-Telegram Desktop-<rand>.desktop` (NoDisplay, that
  Exec) and sets it as the default in `~/.config/mimeapps.list`, which is broken on
  the host. `DESKTOPINTEGRATION` doesn't stop this, and the binary has no other
  switch. The fix gives the two sides different answers:
  - **Host:** the wrapper writes `telegram-box-url-handler.desktop` with
    `Exec=$HOME/.local/bin/telegram-desktop -- %u`, the `bin:` export, and sets
    it in `~/.config/mimeapps.list` with awk: the three keys in
    `[Default Applications]` (added if missing), plus any of them already under
    `[Added Associations]`. It's rewritten only on change.
    - **Why the bin export and not `distrobox enter`:** links are also opened from
      other boxes. Chrome in `chrome-box` runs `xdg-open` *in the box*, and
      `distrobox` doesn't exist there. The `distrobox-export --bin` wrapper runs
      `distrobox-enter` on the host, re-dispatches through `distrobox-host-exec`
      from another box, and execs directly in `telegram-box`.
    - **Why `[Added Associations]` too:** xdg-utils' `xdg-mime query default` in
      a box returned the stale `org.telegram.desktop._<hash>.desktop` from that
      section even after `[Default Applications]` was fixed. xdg-open then
      couldn't find the file and fell back to the browser ("Opening in existing
      browser session").
  - **Telegram:** runs with `XDG_CURRENT_DESKTOP=X-TelegramBox:<original>`. GIO
    reads `~/.config/<desktop>-mimeapps.list` before `mimeapps.list`, so Telegram
    sees `x-telegrambox-mimeapps.list` → `telegram-box-scheme.desktop`, which is
    shipped in the image's `/usr/share/applications` (box-only) with exactly
    Telegram's command line. Telegram finds itself registered and writes nothing.
    The host never reads the x-telegrambox file, since its desktop is X-Cinnamon.
  - **`gio mime` can't set the host default from inside the box:** it fails with
    "Failed to load info for handler", because GIO rejects a desktop entry whose
    Exec program (`distrobox`) isn't on the box's PATH. Hence the awk edit.
  - **Verified 2026-10-11 (Mint/Cinnamon, X11):**
    - After launch, `xdg-mime query default x-scheme-handler/{tg,ton,tonsite}`
      gives the box handler, and it holds across relaunches with no `userapp`
      files recreated.
    - `xdg-open tg://resolve?domain=telegram` with Telegram running starts a
      second instance logging `Command line: /opt/Telegram/Telegram --
      tg://resolve?domain=telegram`, which hands off over the local socket.
    - With Telegram stopped, the same link cold-starts it with the URL.
  - **Link launches detach** (`-- <url>` → `setsid -f`, then exit 0). Without
    that, a cold start from `chrome-box` left `xdg-open` → `distrobox-host-exec`
    → `host-spawn` → `distrobox enter` blocked for as long as Telegram ran.
    Killing that chain did *not* kill Telegram, so this is about callers waiting,
    not about lifetime. Plain launches still `exec`.
  - **Verified 2026-10-11 from `chrome-box`:** with Telegram stopped,
    `xdg-open tg://resolve?domain=telegram` returned in 1s and started Telegram
    with the URL, leaving no waiting `host-spawn`. With it running, the link
    reached a new instance that handed it over. Same two checks on the host. The
    host defaults held, and no `userapp` files came back.
  - Not covered: a host whose desktop sets its own `<desktop>-mimeapps.list`
    entries for these schemes would take precedence over `mimeapps.list`.
- **The built-in updater can't update the install**: `/opt/Telegram` is
  root-owned in the image. `~/.local/share/TelegramDesktop/tupdates/` exists, but
  the update path is `tools setup telegram`.
- State lives in `~/.local/share/TelegramDesktop/` (tdata = session). The log
  records the launched version (`Launched version: 7003001` = 7.3.1 after the 2026-10-11 rebuild; 6.8.2 on
  2026-10-10).
- Launching from a shell prints a harmless Qt notice about the `C` locale
  switching to `C.UTF-8`.
- `git` isn't installed, though the repo convention is to include it so the
  shared-`$HOME` dotfiles work in every box.
