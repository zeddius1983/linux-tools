## opencode

OpenCode is an open-source AI coding agent with a terminal TUI. Packaged as a Distrobox container so it can be exported to the host shell and app menu without polluting the host environment.

## Implementation

- **Base image**: `docker.io/ubuntu:24.04` — minimal, matches other CLI tool apps (codex-cli pattern)
- **Install method**: official install script, chosen by major version: `https://opencode.ai/install` for 0.x/1.x, `https://opencode.ai/v2/install` for 2.x and `latest`. Run with `bash` against a throwaway `HOME=/opt/opencode-install` and `--no-modify-path`
  - The script always installs to `$HOME/.opencode/bin/opencode` (no install-dir option), so the binary is moved to `/usr/bin/opencode` where `command -pv` (system PATH) finds it for distrobox-export
- **Release picker**: `wizard/00-release.buildarg` is a `releases|anomalyco/opencode` page → build arg `OPENCODE_RELEASE` (a tag such as `v1.18.35`; the Dockerfile strips the `v` for the installer's `--version`). Default `latest` goes to the v2 installer, which resolves it to the newest 2.x. `CACHE_BUST` forces the install layer to rerun on every build, same as codex-cli
- **README.md** added in the October 2026 refresh (it was missing, so the dashboard info panel was empty)
- **Exports**:
  - `bin:opencode` — exports binary to `~/.local/bin` on the host for shell use
  - `desktop:opencode:OpenCode` — creates a terminal-launched `.desktop` entry in the app menu
- **No extra flags**: pure TUI, no GPU/device passthrough needed

## Pitfalls and notes

- `/usr/local/bin` is not in the system PATH used by `command -pv`; the binary must be at `/usr/bin/opencode` for exports to work
- Both install scripts set `INSTALL_DIR=$HOME/.opencode/bin` — if this changes in a future version, the `mv` path in the Dockerfile will need updating. The v2 script also writes an `opencode2` shim there, discarded with the throwaway HOME
- **Upstream repo moved** from `sst/opencode` to `anomalyco/opencode` (the installer downloads from the latter)
- **Don't build the release list from git tags.** The repo carried a `2.0.x` line of bare git tags (2.0.26 as of Oct 2026) with no published GitHub release and no assets. A `git ls-remote` picker (the codex-cli/openclaw pattern) would offer versions that can't be downloaded. `releases|` lists only published releases
- **OpenCode 2 broke the single-installer build** (2026-10-27). `v2.2.0` became a published release, so the picker offered it (newest first, the default), and `/install` refused it: `Error: OpenCode 2.2.0 is not an OpenCode 1 release, so this installer can't install it.` The two installers don't overlap: `/install` downloads GitHub release assets and resolves `latest` to the newest **1.x** only; `/v2/install` downloads `@opencode/cli-<target>` from npm, where 1.x builds are not published (404 for 1.18.35), and resolves `latest` from `opencode.ai/update/api/latest/cli/npm`. Hence the `case` on the major version. Verified by building `v2.2.0`, `latest` (→ `opencode v2.2.0`) and `v1.19.4` (→ `1.19.4`). 2.x prints `opencode v2.2.0` for `--version`, 1.x a bare `1.19.4`
- **V1 → V2 for users**: same command and the same config/data locations (`~/.config/opencode`, project `opencode.json(c)`/`.opencode/`), V1 config read as is. Breaking: the plugin API (V1 plugins don't run), the server API contracts, and terminal settings moving from `tui.json(c)` to one global `cli.json` (auto-migrated). Upstream guide: https://opencode.ai/v2/docs/migrate-v1/. A 1.x tag can still be picked to stay on V1
- **The Dockerfile was broken on `main` from #49 (the dashboard prototype) until the refresh**: that commit dropped the gh step's closing `&& rm -rf /var/lib/apt/lists/*`, leaving a trailing `\` that folded the next `RUN` into `apt-get install`. The existing image predated it, so nobody noticed until a rebuild
- The install script uses `set -euo pipefail` and requires bash. Pipe to `bash`, not `sh` — Ubuntu's `sh` is `dash` and will fail with "Illegal option -o pipefail"
- API keys are configured by the user at runtime (not baked into the image)
