## memtest_vulkan

[memtest_vulkan](https://github.com/GpuZelenograd/memtest_vulkan) — a Vulkan-compute
GPU memory stress test. Packaged so a VRAM check is one command on any host,
without a Vulkan SDK or a manual tarball unpack, and so the same binary is
reachable from the app menu.

Vendor-neutral by nature: it needs nothing but a Vulkan 1.1 driver, which is why
the container only has to supply the loader plus Mesa's ICDs, and why NVIDIA
support is purely a passthrough question.

## Implementation

**Base image: `registry.fedoraproject.org/fedora:43`.** Same reasoning as
`nvtop` — Fedora ships a current Mesa, and RADV/ANV quality is what decides
whether a GPU shows up at all. Nothing is compiled here; the base image is
chosen entirely for its drivers.

**Prebuilt binary, pinned to v0.5.0.** Upstream ships a ~850 KB Rust binary in a
`.tar.xz`; it links only glibc (`ldd` shows libc/libm/libdl/libpthread/librt,
nothing else) and is built `for GNU/Linux 2.6.32`, so it runs on any base image.
It is unpacked straight into `/usr/bin` — required, since `command -pv` (used by
the export machinery) does not search `/usr/local/bin`.

**No version picker, by decision.** The original plan had one. Upstream has
published three releases in four years, and the release list is awkward in three
separate ways: `v0.5.0` uses `..._DesktopLinux_X86_64.tar.xz`, `v0.4.0` uses the
older `x86_64-linux-...` scheme, `v0.3.0` has no version in the asset name at
all, there is a `support` "release" holding only Windows DLLs, and a `v0.4.1`
git tag with no release attached. So neither of the repo's two picker idioms
works unmodified — `releases|owner/repo` would offer `support`, and a
`git ls-remote` items-cmd would offer `v0.4.1`, both of which break the build
when chosen. Pinning `ARG MEMTEST_VERSION` was judged the better trade for a
project releasing this rarely. A `wizard/NN-release.buildarg` page feeding that
same ARG is a drop-in addition if upstream ever picks up pace.

**`ARG` without `CACHE_BUST`.** Unlike `codex-cli`/`fastflowlm`, whose downloads
resolve `latest` at build time and therefore must not be cached, this URL is
fully pinned — caching the download layer is correct, and a rebuild after only a
version bump invalidates it naturally. `tools build` still passes `CACHE_BUST`
to every build, so the build log ends with a harmless
`[Warning] one or more build args were not consumed: [CACHE_BUST]`.

**Wizard: one `.runtime` page, AMD/Intel vs NVIDIA (CDI).** Copied from `nvtop`,
for the same reason and with the same two variants: `amd` (no file, so no extra
flags) and `nvidia` (`create_flags.nvidia` = `--device nvidia.com/gpu=all`).

**Exports: `bin:memtest_vulkan`, `bin:memtest_vulkan_verbose`, `desktop:memtest_vulkan`.**
`vulkaninfo` is installed for diagnostics but deliberately not exported, so it
cannot shadow a host copy in `~/.local/bin`.

## Pitfalls and notes

- **The tool parses no command-line arguments at all.** There is no `--help` and
  no flag of any kind; checking the binary's strings turns up no argument
  parser. Everything is driven by the interactive menu, by environment variables
  (`VK_DRIVER_FILES`, `MEMTEST_VULKAN_EMULATE_WRITE_BUG_ITERATION`), or by the
  invoked name. Do not add a wrapper that "passes a flag" — there are none to
  pass.

- **Verbose mode is selected by the binary's own filename.** It prints
  `Verbose feature enabled (or 'verbose' found in name)` and keys off finding
  the substring `verbose` in argv[0]. That is why `memtest_vulkan_verbose` is a
  **symlink** in `/usr/bin` rather than a wrapper script — the export machinery
  runs it by name, so argv[0] carries through and verbose mode engages. A
  wrapper that `exec`s the real binary would lose this.

- **Every run writes `memtest_vulkan.log` into the current working directory** —
  not only on failure, which is what a first read of the strings suggests. From
  the `.desktop` entry that means a file dropped in `$HOME` on each launch. A
  wrapper `cd`-ing into `~/.local/share/memtest_vulkan/` was considered and
  deliberately rejected: it would diverge from every other memtest_vulkan
  install and surprise anyone following upstream's docs. Documented in the
  README instead.

- **`--device nvidia.com/gpu=all` cannot be applied unconditionally.** Verified
  on an AMD-only host with no `/etc/cdi/`:
  `podman run --rm --device nvidia.com/gpu=all <image> true` →
  `Error: setting up CDI devices: unresolvable CDI devices nvidia.com/gpu=all`.
  The box then fails to *start*, and the only symptom the user sees is
  `cannot find 'memtest_vulkan' inside container` from every export lookup. This
  is the whole reason the GPU question exists rather than being hard-coded.

- **`llvmpipe` always shows up in the device menu** and reports a huge memory
  size (system RAM). It is Mesa's CPU rasteriser, pulled in by
  `mesa-vulkan-drivers` and not separable from the RADV/ANV ICDs that are the
  point of that package. Upstream documents the same thing on bare metal; it is
  not a packaging artefact. The tool's default (device 1) picks the real GPU.

- **Without a tty the 10-second autoselect is skipped entirely.** Piping stdin
  from `/dev/null` prints `...testing default device confirmed` and starts
  immediately on device 1. Useful for a scripted smoke test; it also means a
  non-interactive invocation can never be steered to a different device except
  via `VK_DRIVER_FILES`.

- **v0.5.0 runs a bounded "standard 5-minute test" and exits on its own**, unlike
  the older versions upstream's README documents ("wait at least 6 minutes and
  stop by Ctrl+C"). Worth knowing before assuming a run that ended by itself was
  interrupted.

- **On unified-memory APUs the reported size is not VRAM.** Strix Halo
  (`AMD Radeon 8060S / RADV GFX1151`) reports ~83 GB and tests a GTT allocation
  out of system RAM at ~190 GB/s. Valid as a memory-path test, but it is not a
  discrete-VRAM result, and it puts real pressure on system RAM while running.

- **Two harmless verbose-mode warnings**: `Layer 0 does not exist in the list of
  available layers` (no validation layers in the image; the tool retries without
  them and continues) and `Received return code -9 ... libvulkan_dzn.so`
  (Mesa's Dozen D3D12 ICD, which has nothing to bind to on Linux and is
  skipped). Neither indicates a problem; don't "fix" them by adding packages.
