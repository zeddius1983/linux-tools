## lmstudio

LM Studio desktop app (local-LLM runner), packaged from the official AppImage.
Fedora 43 base (for the Vulkan/GL userspace). Exported to the host menu via
`app:lmstudio` (LM Studio installs its own `.desktop` inside the container).

The distinguishing feature is a **setup-time GPU runtime picker** that chooses
between:
- **AMD (ROCm/Vulkan)** — `/dev/kfd` + `/dev/dri` passthrough, Mesa Vulkan (default)
- **NVIDIA (CUDA)** — CDI device `--device nvidia.com/gpu=all` (podman, via
  `--additional-flags`), NOT `distrobox --nvidia` (see pitfall below)

## Implementation

**Picker mechanism (reusable, added to the core pipeline, not just this app):**

- New wizard page type `.runtime` in `lib/wizard.sh` — a `whiptail --radiolist`.
  Body lines are `Label|value|description`; the first line is the default. The
  **Label is shown verbatim** (e.g. `AMD (ROCm/Vulkan)`) and whiptail returns the
  Label; `wizard_create_variant()` translates the stored Label back to its
  filename-safe `value` (amd/nvidia) by re-reading the page.
- `cmd_create` in `lib/commands.sh` consults `wizard_create_variant`:
  - `create_flags.<value>` overrides the default `create_flags` (podman
    `--additional-flags`) if present.
  - `create_args.<value>` supplies **distrobox-level** args appended directly to
    the `distrobox create` line — this is how `--nvidia` gets in, since it is NOT
    a podman flag and can't go through `--additional-flags`.
  - No wizard selection (non-interactive `tools create`) → plain `create_flags`,
    preserving prior behavior.

**App files:**
- `wizard/00-runtime.runtime` — the two-option picker.
- `create_flags` — AMD default (`--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 ...`).
- `create_flags.nvidia` — NVIDIA podman flags: `--device nvidia.com/gpu=all`
  (CDI) + `--device /dev/dri --group-add 44 --group-add 992 ...`; no `/dev/kfd`
  (AMD-only). There is intentionally NO `create_args.nvidia` — CDI needs no
  distrobox-level flag, everything goes through podman `--additional-flags`.
- Dockerfile is unchanged from the original AMD-oriented image (Mesa Vulkan etc.).

## Pitfalls and notes

- **A CUDA runtime is BUNDLED in the AppImage** — under
  `resources/app/.webpack/bin/extensions/backends/llama.cpp-linux-x86_64-nvidia-cuda-avx2-*`
  (ships `libggml-cuda.so`, `libcudart.so.11` → CUDA 11.8). LM Studio auto-selects
  the engine matching detected hardware on first launch. NOTE (verified on the
  RTX 3080 box): it does not just use the bundled one — it **downloads a newer
  CUDA 12 engine** on first launch. So the network fetch is small but real; the
  point is it's automatic (no manual runtime picking) and the picker needs no
  build-arg / image change. Downloaded engine lives in shared `~/.lmstudio/`.

- **You cannot headlessly pre-install/pre-select a runtime at `tools setup` time.**
  The bundled `lms` CLI (`.webpack/lms`, an ELF) *does* support non-interactive
  `lms runtime select <alias>` and `lms runtime get 'llama.cpp:cuda' -y`, BUT every
  runtime command needs the LM Studio **daemon**, and `lms bootstrap` / `lms server
  start` refuse with "Cannot find LM Studio installation … run it at least once"
  until the GUI app has run once (which needs a display). Conclusion from the probe:
  don't script `lms` during setup — rely on bundle + auto-select instead. The README
  documents the `lms runtime ls/select` fallback for after first launch.

- **DO NOT use `distrobox create --nvidia` here — it hangs.** First attempt used
  `--nvidia` (via a `create_args.nvidia` file, since `--nvidia` is a distrobox-level
  flag not a podman one). On this CachyOS + rootless-podman host it wedged in a
  retry loop: distrobox's nvidia hook bind-mounts the *entire* host driver
  (~97 libs) into the container on every start, and it got stuck re-mounting
  `libEGL_nvidia.so.0` forever (mount count flatlined at 231, container init
  stuck in a `sleep 15` retry loop — visible via `podman logs lmstudio-box` and
  `grep -c nvidia /proc/$(podman inspect lmstudio-box -f '{{.State.Pid}}')/mountinfo`).
  Even when it "works" it re-runs the slow integration on every launch.
  **Fix: CDI.** `sudo pacman -S nvidia-container-toolkit` +
  `sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`, then podman
  `--device nvidia.com/gpu=all`. Single declarative injection, fast, no loop.
  Requires the CDI spec to exist on the host (see README prerequisite); without
  it, create fails with podman "no such device nvidia.com/gpu=all".

- **The `create_args.<variant>` mechanism in cmd_create still exists** (appends
  distrobox-level flags) and is harmless/unused now that lmstudio dropped
  `--nvidia`. Keep it — it's the only way to pass true distrobox flags if a
  future app needs one; it just isn't needed for CDI.

- **Mesa Vulkan in the image is AMD/Intel-only.** On the NVIDIA box it's unused
  dead weight (harmless). NVIDIA's Vulkan ICD + libcuda come from the host driver
  via `--nvidia`. Kept a single image rather than varying by build-arg because the
  choice is purely runtime GPU passthrough.

- **Storage is in shared host home `~/.lmstudio/`** (models, extracted backends,
  settings incl. selected runtime). Survives rebuilds and is shared across vendor
  switches. Baking anything into the image's `~/.lmstudio` is pointless — build
  runs as root (`/root`), runtime uses the host user's home.

- The original app had no `create_flags` at all; the default box still saw the GPU
  PCI node (distrobox shares `/dev`) but with `driver (null)` — i.e. no usable GPU
  userspace without the explicit passthrough the picker now adds.
