## comfyui

Node-based UI for generative AI image and video workflows (Stable Diffusion, SDXL, Flux, WAN video, etc.). Packaged as a Distrobox container with a **setup-time GPU picker** (AMD/ROCm or NVIDIA/CUDA) and a **release picker** (upstream ComfyUI release tags). The AMD path is the default and is tuned for Strix Halo (gfx1151) unified memory.

## Implementation

**Two wizard pages** (both consumed at build time, so re-running `tools setup comfyui` is how you switch either):

- `wizard/00-gpu.runtime` — `AMD (ROCm)|amd` / `NVIDIA (CUDA)|nvidia`. Carries an `arg|COMFY_GPU` line, so the one answer drives **both** the base image (`--build-arg COMFY_GPU=`) and the create-time flags (`create_flags.nvidia`). Applicable to `setup,build,create`.
- `wizard/01-release.buildarg` — `arg|COMFY_REF`, `releases|Comfy-Org/ComfyUI` (the repo `comfyanonymous/ComfyUI` now redirects to), plus `extra|master`. Applicable to `setup,build`. The `releases|` line replaced a hand-written `curl | grep | sed` items-cmd: the dashboard now calls the API itself, so the picker shows each release's date and notes. `master` is a branch, not a release — that is exactly what `extra|` is for, and it is listed last with no notes.

**Core change this app required** (in `lib/wizard.sh`, `tui/wizard.go`, `tui/wizardui.go`): `.runtime` pages may now carry an optional `arg|<BUILD_ARG_NAME>` config line, which additionally emits `--build-arg <NAME>=<value>` for the selected variant *value*. Before this, `.runtime` only fed `cmd_create` and `.buildarg` only fed `cmd_build`, so a GPU choice that changes the base image would have needed the user to answer the same question twice. `arg` is now a reserved line key in `.runtime` bodies and cannot be an option Label.

**Base images** (selected by `FROM base-${COMFY_GPU}`):

| Variant | Base | PyTorch |
|---|---|---|
| `amd` (default) | `docker.io/rocm/pytorch:rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.10.0` | pre-installed in `/opt/venv` |
| `nvidia` | `docker.io/nvidia/cuda:12.8.1-cudnn-runtime-ubuntu24.04` | `pip install torch torchvision torchaudio --index-url .../whl/cu128` into a hand-made `/opt/venv` |

`/opt/venv` is used on the NVIDIA side deliberately, to match the path the ROCm base image already uses — that keeps the wrapper scripts and every "call `/opt/venv/bin/python` explicitly" note true for both variants.

**Install path**: `/opt/ComfyUI`, cloned at image-build time with `--depth=1 --branch "${COMFY_REF}"` (works for both tags and `master`).

**Model storage**: `~/.comfyui/models/` via `extra_model_paths.yaml`. Lives in shared `$HOME` so models survive rebuilds and are shared across GPU variants. Sub-dirs: checkpoints, vae, loras, controlnet, upscale_models, clip, unet, diffusion_models.

**Plugins**: ComfyUI-Manager pre-installed at `custom_nodes/ComfyUI-Manager`; users install further nodes from the UI. Custom nodes are inside the image, so they are lost on rebuild — reinstalling from the Manager UI is the intended path.

**Wrappers**: now real files (`comfyui-run` → `/usr/bin/comfyui`, `comfyui-app`) `COPY`-ed in, not `printf`-ed. The GPU-conditional launcher logic was past the point where an escaped one-liner was readable. `comfyui-run` reads `/etc/comfyui-gpu` (written by each base stage) to pick its tuning, and honours `COMFYUI_ARGS` as a wholesale override of the built-in flag set.

**Stopping**: `comfyui-stop` (exported as `bin:`) exists because the desktop launcher starts the server detached — no terminal, so no Ctrl-C. It POSTs `/interrupt`, then sends **SIGINT**, escalating to SIGKILL after 30s. SIGINT rather than SIGTERM on purpose: SIGINT is what Ctrl-C sends, so Python raises `KeyboardInterrupt` and unwinds normally, while SIGTERM's default action kills the interpreter with no cleanup. It refuses to stop while prompts are queued (they are in-memory and die with the process) unless `--force` is passed.

**Tray icon**: `comfyui-tray`, a GTK3 + AyatanaAppIndicator3 StatusNotifierItem with live status and Start/Stop/Open/Log items. `comfyui-app` starts it best-effort alongside the server so a desktop-launched (detached, no terminal) server is still controllable. Browser-opening was split out of `comfyui-app` into `comfyui-open` so the tray reuses it instead of re-entering the launcher. Single-instance via `flock` on `~/.comfyui/tray.lock`. Stop runs on a worker thread so the menu never freezes, and surfaces `comfyui-stop`'s queued-prompt refusal as a "Stop anyway" dialog.

**Export type**: `gui:comfyui-app:ComfyUI` + `bin:comfyui` + `bin:comfyui-stop` + `bin:comfyui-tray`. The tray deliberately has **no** `gui:` entry — `comfyui-app` starts it, so a second menu icon is pure clutter (this was tried and removed). The `bin:` export stays so it can be relaunched after **Close** and pointed at by a hand-written autostart entry. The close item is named "Close" (not "Quit tray") and **stops the server before closing** — closing without it strands a server with no icon, no window and no terminal. A confirm-on-close dialog and a hard-disabled item were both considered and rejected in favour of just doing it. The queued-prompts "Stop anyway" prompt still applies, and declining it cancels the close too, since keeping the queue while stranding the server is the worst of both. ComfyUI is a web server; access via browser at http://localhost:8188.

**create_flags**: AMD default is `--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 --security-opt seccomp=unconfined --ipc=host`. `create_flags.nvidia` swaps `/dev/kfd` for the CDI device `--device nvidia.com/gpu=all`. There is intentionally no `create_flags.amd` — `cmd_create` falls back to the plain `create_flags` file, which is also what a non-interactive create gets.

## Pitfalls and notes

- **`FROM base-${COMFY_GPU}` does not build the unselected stage.** Verified with podman/buildah on this host: building with `COMFY_GPU=nvidia` starts at stage `[2/3]` and never pulls the AMD base at all. This is what makes the pattern viable here — the ROCm image is 15–20 GB, and pulling it to build an NVIDIA image would be unacceptable. An `ARG` used in a `FROM` line must be declared **before** the first `FROM`, and re-declared after it to be visible to `RUN`.
- **`extra_model_paths.yaml` only relocates *models*.** ComfyUI's `output/`, `input/` and `user/` still default to inside `/opt/ComfyUI`, and `tools setup` deletes the image — so a rebuild silently destroyed generated images and, worse, **saved workflows** (`user/` holds workflows and UI settings, not scratch state). The launcher now passes `--output-directory`, `--input-directory` and `--user-directory` under `~/.comfyui/`. `--base-directory` would cover all of them in one flag but also relocates `custom_nodes`, which breaks the baked-in ComfyUI-Manager — hence three explicit flags.
  - `COMFYUI_ARGS` deliberately replaces only the GPU *tuning* array, never these; an override that dropped them would quietly restore the data-loss path.
  - Anyone upgrading from an image built before 2026-08-05 must rescue `/opt/ComfyUI/output` and `/opt/ComfyUI/user` out of the old box *before* re-running setup — see the README's "Upgrading from a build before this redirect".
- **`--database-url` does not follow `--user-directory`, and redirecting the user dir without it breaks startup.** ComfyUI 0.30 keeps an asset DB whose default path is computed *at import time* from the install dir (`database_default_path` in `comfy/cli_args.py` → `/opt/ComfyUI/user/comfyui.db`). Once `--user-directory` points elsewhere, nothing creates `/opt/ComfyUI/user`, so SQLite gets `unable to open database file` and ComfyUI logs `Failed to initialize database` (non-fatal today — it warns the DB "will be required" in future). Caught only by reading the startup log after a real rebuild; the server comes up and serves normally, so an HTTP 200 check does not catch it. The launcher now passes `--database-url "sqlite:///${HOME}/.comfyui/user/comfyui.db"`, which also puts the DB where a rebuild cannot delete it.
  - Note the four slashes: `sqlite:///` + an absolute path that already starts with `/`.
- **Git refuses to operate in `/opt/ComfyUI`: "detected dubious ownership".** The repos are cloned by root at build time and used by uid 1000 at runtime. This breaks ComfyUI-Manager, which drives updates and custom-node installs through git — the exact path the README recommends after a rebuild. Fixed with `git config --system --add safe.directory` for `/opt/ComfyUI` and `/opt/ComfyUI/custom_nodes/ComfyUI-Manager`. Nodes the Manager installs later are user-owned and need no entry, which is just as well: `safe.directory` supports only a bare `*` (all repos), not partial globs like `/opt/ComfyUI/custom_nodes/*`.
- **A non-interactive NVIDIA install needs `VARIANT`, not just `BUILD_ARGS`.** `--build-arg COMFY_GPU=nvidia` only affects the image; `cmd_create` reads `wizard_create_variant`, so without `VARIANT="nvidia"` in the state file it falls back to the plain `create_flags` — `/dev/kfd`, no CDI device — and on an NVIDIA-only host the box fails to create or comes up with no usable GPU. The two must be set together and kept in agreement.
- **`set -o pipefail` + `grep -q` is a false-negative machine, and it is what made the launcher open the default browser instead of Chrome.** `distrobox-host-exec distrobox list | grep -q chrome-box`: `grep -q` exits at the first match and closes the pipe, the producer dies of SIGPIPE (141), and `pipefail` reports that 141 as the pipeline's status — so the probe reads "absent" *exactly when the thing is present*, and only when the match is not on the last line. The original `comfyui-app` had no `set -euo pipefail`, so this was introduced by splitting the logic into `comfyui-open` with strict mode added. Fix: capture then match (`list="$(... || true)"; [[ "$list" == *chrome-box* ]]`), never a pipe that can be broken.
  - **Verification lesson**: this survived one round of "fixing" because the check was re-typed by hand into a `bash -c` *without* strict mode, and with `grep -c` (which reads all input and never triggers SIGPIPE) instead of `grep -q`. That tested a different program than the one shipped. Trace the real file — `distrobox enter <box> -- bash -x /usr/bin/<script>` — and read which branch it takes.
- **The "first `distrobox-host-exec` call in a new box silently returns nothing" pitfall bites `comfyui-open` specifically, and only on the first launch after `tools setup`.** The chrome-box probe (`distrobox-host-exec distrobox list | grep -q chrome-box`) was the first such call in the freshly created box; it produced no output while host-spawn bootstrapped, so the script concluded there was no chrome-box and downgraded to `xdg-open` — the user got their default browser instead of an app window, exactly once, and it worked ever after. Confirmed by timestamps: box created 01:05:37, `/usr/bin/host-spawn` written 01:06:34, i.e. the launcher's own call installed it. Fix: a throwaway `distrobox-host-exec true` to absorb the bootstrap, then probe with one retry.
  - Generalisable: **never let the first `distrobox-host-exec` in a script be a probe whose empty output means "feature absent"** — empty is indistinguishable from "not bootstrapped yet".
- **`less` on the ComfyUI log needs `-R`, or the terminal flashes open and shuts.** ComfyUI colours its log with ANSI escapes; without `-R`, `less` decides the file is binary and prompts `"…server.log" may be a binary file. See it anyway?`, which against `+F` ends in an immediate exit. ghostty reports it only as `abnormal process exit detected` — the actual prompt is invisible unless you capture the pager's own output (`ghostty -e bash -c 'exec >~/.lessdbg 2>&1; less +F …'`). The tray's Show log therefore runs `less -r -f +F`. **-f is what suppresses the binary prompt, not -r** — `-r` only changes how control chars are *displayed*, and less still counts them toward its binary heuristic. `-R` happens to suppress the prompt too (it treats the escapes as known-good), which is precisely why testing with `-R` hid the bug and a user running `less -r` hit it immediately. Measured under a pty on the real log: `-r` prompts, `-R` does not, `-f -r` does not. **-r, not -R**, because: tqdm redraws its progress bars with carriage returns, and -R forwards only colour escapes while rendering every other control char literally, so each intermediate redraw appears as `^M  5%|...^M 30%|...` strung along one line. -r forwards CR as well, so the terminal overwrites in place and a finished bar reads as one `100%|####|`, exactly as `tail -f` shows it. Measured under a pty: -R emitted 2 literal `^M` for a CR-redrawn line, -r emitted 0, both keeping colour. The documented cost of -r is that less can misjudge the width of lines holding control chars, smearing horizontal scrolling -- acceptable for a log.
  - **ghostty silently eats `+`-prefixed arguments.** `ghostty -e less -r -f +F FILE` starts `less -r -f FILE` — follow mode just never happens, with no error anywhere. Confirmed by reading the child's cmdline: `ps -eo pid,ppid,args | grep -w less` shows ghostty's own argv still holding `+F` while the `less` it spawned does not. The symptom is "`+F` doesn't work but pressing F does". Fix: hand the terminal `bash -c 'exec less -r -f +F "$1"' _ <file>` so the `+F` sits inside a quoted string the terminal's parser never inspects. Do this regardless of terminal — it costs nothing and no other terminal is known-safe.
  - **`ov` is NOT a substitute here, despite looking like one.** It renders ANSI cleanly and never raises the binary prompt, but it *swallows carriage returns*: measured on this log, `ov -f` and `ov --converter raw -f` both emit `raw_CR=0` while `less -r -f +F` emits 55. Passing CR through is the entire mechanism that makes a tqdm bar overwrite in place, so under ov every intermediate percentage ends up side by side on one enormous line. It was shipped briefly on the strength of a probe that counted literal `^M` — ov scores 0 there *and* renders wrongly, so that metric cannot tell the two apart. **Measure `raw_CR` passthrough, not the absence of `^M`.** `ov` stays in shell-toolbox as a general pager; it is simply the wrong tool for a CR-redrawn log.
  - The terminal must be the **host's** (`distrobox-host-exec <term> <flag> less -R +F <log>`): this container ships none, and the log is in the shared `$HOME` the host can read directly. `host_terminal()` probes the same list as `pick_terminal()` in `lib/helpers.sh`, warms host-spawn first (the first-call trap again), caches the answer, and runs the probe on a startup thread so the first click is not blocked.
- **`comfyui-tray` must hardcode `#!/usr/bin/python3` — the usual "always use `/opt/venv/bin/python`" rule is inverted here.** `python3-gi` installs into the *system* interpreter's `/usr/lib/python3/dist-packages`, and `/opt/venv` has no `gi`. Because the Dockerfile puts `/opt/venv/bin` first on `PATH`, `#!/usr/bin/env python3` resolves to the venv interpreter and the tray dies with `ModuleNotFoundError: No module named 'gi'`. The tray needs PyGObject and never needs torch, so the system interpreter is correct — but only if the shebang is absolute.
- **A tray icon installed under `/usr/` in the container is invisible, and everything else about the tray still works.** StatusNotifierItem passes the panel only an icon *name* and a *theme path*; the panel then opens the file itself — and the panel process (`xapp-sn-watcher` on Cinnamon, `plasmashell` on KDE) runs on the **host**, where nothing the container puts under `/usr/share` exists. The item registers, the menu opens, every action works, and no icon is drawn. From inside the container the path resolves perfectly (`Gtk.IconTheme.lookup_icon` finds it), which makes this very easy to "verify" as working. Fix: `comfyui-tray` stages the PNG into `~/.comfyui/icons/` at startup (shared `$HOME`, so both sides see it) and passes *that* as the theme path.
  - **Verification rule this teaches**: for anything crossing the container/host boundary, check the path from the side that *consumes* it (`distrobox-host-exec ls -l "$path/$name.png"`), never from the side that produces it.
  - The app icon for the `.desktop` is unaffected: `resolve_icon` in `lib/helpers.sh` returns a path under `$APPS_DIR`, which is in the shared home already.
- **Verifying a tray icon actually appeared: query the watcher, don't grep bus names.** `busctl --user list | grep StatusNotifierItem` finds nothing even when the icon is working — libayatana registers through the watcher under a *unique* connection name, not a well-known `org.kde.StatusNotifierItem-*` one. The real check is `busctl --user get-property org.kde.StatusNotifierWatcher /StatusNotifierWatcher org.kde.StatusNotifierWatcher RegisteredStatusNotifierItems`, which lists e.g. `:1.2179/org/ayatana/NotificationItem/comfyui`; from there `get-property <conn> <path> org.kde.StatusNotifierItem IconName/IconThemePath/Status/Menu` confirms the icon resolves and the menu is exported. The `Couldn't register with accessibility bus` warning in the log is benign and unrelated.
- **A background `nohup cmd &` in a non-interactive shell makes the child ignore SIGINT — permanently, and silently.** POSIX has a shell with job control *disabled* start async children with SIGINT and SIGQUIT set to `SIG_IGN`, and CPython checks the disposition at startup: if SIGINT is already ignored it deliberately does **not** install its `KeyboardInterrupt` handler. The result is a ComfyUI server that discards every SIGINT forever, so `pkill -INT` looks like it does nothing (and `pkill` is silent on both success and no-match, which hides it further). Confirmed on the real process via `SigIgn` in `/proc/<pid>/status` (`0000000001001007` — bit 1 set; SIGHUP from `nohup` and SIGQUIT likewise ignored, SIGTERM left at default).
  - Fix in `comfyui-app`: `set -m` around the launch. Job control on means bash does *not* force the ignore, so Python installs its handler normally. `nohup` still covers SIGHUP, which is all it was ever doing. Verified: same launch is `IGNORED` without `set -m`, `caught` with it.
  - `comfyui-stop` cannot assume the fix is present — images built earlier still run the old launcher — so it reads `SigIgn` per pid and sends SIGTERM instead of SIGINT to any process that ignores SIGINT. Both paths stop in ~1s instead of falling through to the 30s SIGKILL.
- **`pgrep -f`/`pkill -f` self-matching is a real trap when testing this.** A harness that puts the pattern (`/opt/venv/bin/python main.py`) inline in a `bash -c` string makes bash's *own* cmdline match, so `pgrep -f` reports a live process long after the target is gone — which looks exactly like `comfyui-stop` failing to kill it. `comfyui-stop` itself is not exposed (its pattern is a shell variable, never on its command line), but test scripts must live in a file, not an inline `-c`.
- **`/opt` permissions**: `/opt/ComfyUI` is installed by root during the image build. ComfyUI creates `user/`, `output/`, `temp/` at runtime and fails with `PermissionError` if the Distrobox user can't write there. Fix: `RUN chmod -R a+rwX /opt/ComfyUI`.
- **`rocm/pytorch` venv**: all packages are in `/opt/venv`, not the system Python. Wrappers must use `/opt/venv/bin/python` explicitly — bare `python` resolves to `/usr/bin/python` which has no site-packages. The NVIDIA stage reproduces this layout rather than diverging.
- **NVIDIA needs a host CDI spec.** `--device nvidia.com/gpu=all` requires `/etc/cdi/nvidia.yaml` (`nvidia-ctk cdi generate`), regenerated after every driver update. Missing it fails at `distrobox create` with podman's "no such device". Do NOT use `distrobox create --nvidia` — see `apps/lmstudio/.memory.md` for the remount-loop post-mortem.
- **CUDA 12.8 wheels need host driver ≥ 570.** Older drivers need `CUDA_BASE` + `TORCH_CUDA_INDEX` dropped to a matching pair (e.g. cu126).
- **NVIDIA image is `-runtime`, not `-devel`** — no `nvcc`. Custom nodes that compile CUDA kernels from source will fail; switching `CUDA_BASE` to the `-devel` tag is the escape hatch (much larger image).
- **`--group-add render/video` on Ubuntu**: use numeric GIDs (`--group-add 992 --group-add 44`) — Ubuntu images don't have these groups in `/etc/group` and Podman fails to start the container if they're missing.
- **`--disable-mmap` is critical for Strix Halo**: memory mapping above 64 GB is very slow on gfx1151 due to a ROCm/driver bug (documented as of early 2026). Causes hangs during model load if omitted. AMD-only; may be fixed in future ROCm releases.
- **`--bf16-vae`**: prevents OOM during VAE decode with Strix Halo unified memory.
- **`--cache-none`**: disables model caching; helps manage GTT vs RAM allocation on large unified memory systems.
- **`--reserve-vram 3`**: recommended for 16 GB+ VRAM (reserves 3 GB for system + PyTorch overhead).
- **The AMD flag set is Strix-Halo-specific and wrong for a small discrete card.** `COMFYUI_ARGS` replaces it wholesale rather than forcing a rebuild.
- **`TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`**: enables AOTriton kernels for gfx1151 — required for good performance.
- **`TORCH_BLAS_PREFER_HIPBLASLT=1`**: enables recent hipBLASLt improvements for gfx1151 (ROCm/rocm-libraries#3913, #3879).
- **`HSA_ENABLE_SDMA=0`**: disables SDMA engine; improves stability on AMD consumer GPUs.
- **MIOpen first-run slowness**: first generation takes ~2× longer while MIOpen compiles GPU kernels. Cache persists at `~/.cache/miopen` across runs.
- **base image size**: `rocm/pytorch` images are 15–20 GB. Build + pull time is significant.
- **rocm/pytorch image version**: `ROCM_BASE` is a build arg, so a newer tag can be tried without editing the Dockerfile. Newer tags exist (`rocm7.14_*`) but 7.2.4 is the one confirmed working on gfx1151 here — don't bump it blind.
- **pip install during build**: `pip install -r requirements.txt` skips torch/torchvision/torchaudio because they are already satisfied by the stage's PyTorch.
