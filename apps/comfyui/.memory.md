## comfyui

Node-based UI for generative AI image and video workflows (Stable Diffusion, SDXL, Flux, WAN video, etc.). Packaged as a Distrobox container with a **setup-time GPU picker** (AMD/ROCm or NVIDIA/CUDA) and a **release picker** (upstream ComfyUI release tags). The AMD path is the default and is tuned for Strix Halo (gfx1151) unified memory.

## Implementation

**Two wizard pages** (both consumed at build time, so re-running `tools setup comfyui` is how you switch either):

- `wizard/00-gpu.runtime` — `AMD (ROCm)|amd` / `NVIDIA (CUDA)|nvidia`. Carries an `arg|COMFY_GPU` line, so the one answer drives **both** the base image (`--build-arg COMFY_GPU=`) and the create-time flags (`create_flags.nvidia`). Applicable to `setup,build,create`.
- `wizard/01-release.buildarg` — `arg|COMFY_REF`, items from the GitHub releases API for `Comfy-Org/ComfyUI` (the repo `comfyanonymous/ComfyUI` now redirects to), plus a trailing `master` option. Applicable to `setup,build`.

**Core change this app required** (in `lib/wizard.sh`, `tui/wizard.go`, `tui/wizardui.go`): `.runtime` pages may now carry an optional `arg|<BUILD_ARG_NAME>` config line, which additionally emits `--build-arg <NAME>=<value>` for the selected variant *value*. Before this, `.runtime` only fed `cmd_create` and `.buildarg` only fed `cmd_build`, so a GPU choice that changes the base image would have needed the user to answer the same question twice. `arg` is now a reserved line key in `.runtime` bodies and cannot be an option Label.

**Base images** (selected by `FROM base-${COMFY_GPU}`):

| Variant | Base | PyTorch |
|---|---|---|
| `amd` (default) | `docker.io/rocm/pytorch:rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.10.0` | pre-installed in `/opt/venv` |
| `nvidia` | `docker.io/nvidia/cuda:12.8.1-cudnn-runtime-ubuntu24.04` | `pip install torch torchvision torchaudio --index-url .../whl/cu128` into a hand-made `/opt/venv` |

`/opt/venv` is used on the NVIDIA side deliberately, to match the path the ROCm base image already uses — that keeps the wrapper scripts and every "call `/opt/venv/bin/python` explicitly" note true for both variants.

**Install path**: `/opt/ComfyUI`, cloned at image-build time with `--depth=1 --branch "${COMFY_REF}"` (works for both tags and `master`).

**Model storage**: `~/.comfyui/models/` via `extra_model_paths.yaml`. Lives in shared `$HOME` so models survive rebuilds and are shared across GPU variants. Sub-dirs: checkpoints, vae, loras, controlnet, upscale_models, clip, unet, diffusion_models.

**Plugins**: ComfyUI-Manager pre-installed at `custom_nodes/ComfyUI-Manager`; users install further nodes from the UI. Custom nodes are inside the image, so they are lost on rebuild — reinstalling from the Manager UI is the intended path.

**Wrappers**: now real files (`comfyui-run` → `/usr/bin/comfyui`, `comfyui-app`) `COPY`-ed in, not `printf`-ed. The GPU-conditional launcher logic was past the point where an escaped one-liner was readable. `comfyui-run` reads `/etc/comfyui-gpu` (written by each base stage) to pick its tuning, and honours `COMFYUI_ARGS` as a wholesale override of the built-in flag set.

**Stopping**: `comfyui-stop` (exported as `bin:`) exists because the desktop launcher starts the server detached — no terminal, so no Ctrl-C. It POSTs `/interrupt`, then sends **SIGINT**, escalating to SIGKILL after 30s. SIGINT rather than SIGTERM on purpose: SIGINT is what Ctrl-C sends, so Python raises `KeyboardInterrupt` and unwinds normally, while SIGTERM's default action kills the interpreter with no cleanup. It refuses to stop while prompts are queued (they are in-memory and die with the process) unless `--force` is passed.

**Export type**: `gui:comfyui-app:ComfyUI` (starts server, opens browser app window) + `bin:comfyui` + `bin:comfyui-stop` (PATH entries). ComfyUI is a web server; access via browser at http://localhost:8188.

**create_flags**: AMD default is `--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 --security-opt seccomp=unconfined --ipc=host`. `create_flags.nvidia` swaps `/dev/kfd` for the CDI device `--device nvidia.com/gpu=all`. There is intentionally no `create_flags.amd` — `cmd_create` falls back to the plain `create_flags` file, which is also what a non-interactive create gets.

Confirmed working as of 2026-06-05 (AMD path) with `rocm/pytorch:rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.10.0`: ComfyUI 0.24.0, ROCm 7.2, gfx1151 detected, NORMAL_VRAM with 131 GB unified memory.

## Pitfalls and notes

- **`FROM base-${COMFY_GPU}` does not build the unselected stage.** Verified with podman/buildah on this host: building with `COMFY_GPU=nvidia` starts at stage `[2/3]` and never pulls the AMD base at all. This is what makes the pattern viable here — the ROCm image is 15–20 GB, and pulling it to build an NVIDIA image would be unacceptable. An `ARG` used in a `FROM` line must be declared **before** the first `FROM`, and re-declared after it to be visible to `RUN`.
- **`extra_model_paths.yaml` only relocates *models*.** ComfyUI's `output/`, `input/` and `user/` still default to inside `/opt/ComfyUI`, and `tools setup` deletes the image — so a rebuild silently destroyed generated images and, worse, **saved workflows** (`user/` holds workflows and UI settings, not scratch state). The launcher now passes `--output-directory`, `--input-directory` and `--user-directory` under `~/.comfyui/`. `--base-directory` would cover all of them in one flag but also relocates `custom_nodes`, which breaks the baked-in ComfyUI-Manager — hence three explicit flags.
  - `COMFYUI_ARGS` deliberately replaces only the GPU *tuning* array, never these; an override that dropped them would quietly restore the data-loss path.
  - Anyone upgrading from an image built before 2026-08-05 must rescue `/opt/ComfyUI/output` and `/opt/ComfyUI/user` out of the old box *before* re-running setup — see the README's "Upgrading from a build before this redirect".
- **A non-interactive NVIDIA install needs `VARIANT`, not just `BUILD_ARGS`.** `--build-arg COMFY_GPU=nvidia` only affects the image; `cmd_create` reads `wizard_create_variant`, so without `VARIANT="nvidia"` in the state file it falls back to the plain `create_flags` — `/dev/kfd`, no CDI device — and on an NVIDIA-only host the box fails to create or comes up with no usable GPU. The two must be set together and kept in agreement.
- **`pgrep -f`/`pkill -f` self-matching is a real trap when testing this.** A harness that puts the pattern (`/opt/venv/bin/python main.py`) inline in a `bash -c` string makes bash's *own* cmdline match, so `pgrep -f` reports a live process long after the target is gone — which looks exactly like `comfyui-stop` failing to kill it. `comfyui-stop` itself is not exposed (its pattern is a shell variable, never on its command line), but test scripts must live in a file, not an inline `-c`.
- **`/opt` permissions**: `/opt/ComfyUI` is installed by root during the image build. ComfyUI creates `user/`, `output/`, `temp/` at runtime and fails with `PermissionError` if the Distrobox user can't write there. Fix: `RUN chmod -R a+rwX /opt/ComfyUI`.
- **`rocm/pytorch` venv**: all packages are in `/opt/venv`, not the system Python. Wrappers must use `/opt/venv/bin/python` explicitly — bare `python` resolves to `/usr/bin/python` which has no site-packages. The NVIDIA stage reproduces this layout rather than diverging.
- **NVIDIA needs a host CDI spec.** `--device nvidia.com/gpu=all` requires `/etc/cdi/nvidia.yaml` (`nvidia-ctk cdi generate`), regenerated after every driver update. Missing it fails at `distrobox create` with podman's "no such device". Do NOT use `distrobox create --nvidia` — see `apps/lmstudio/.memory.md` for the remount-loop post-mortem.
- **CUDA 12.8 wheels need host driver ≥ 570.** Older drivers need `CUDA_BASE` + `TORCH_CUDA_INDEX` dropped to a matching pair (e.g. cu126).
- **NVIDIA image is `-runtime`, not `-devel`** — no `nvcc`. Custom nodes that compile CUDA kernels from source will fail; switching `CUDA_BASE` to the `-devel` tag is the escape hatch (much larger image).
- **`--group-add render/video` on Ubuntu**: use numeric GIDs (`--group-add 992 --group-add 44`) — Ubuntu images don't have these groups in `/etc/group` and Podman fails to start the container if they're missing.
- **`--disable-mmap` is critical for Strix Halo**: memory mapping above 64 GB is very slow on gfx1151 due to a ROCm/driver bug (documented as of early 2026). Causes hangs during model load if omitted. AMD-only; may be fixed in future ROCm releases.
- **`--bf16-vae`**: prevents OOM during VAE decode with Strix Halo unified memory.
- **`--cache-none`**: disables model caching; helps manage GTT vs RAM allocation on large unified memory systems.
- **`--reserve-vram 3`**: recommended for 16 GB+ VRAM (reserves 3 GB for system + PyTorch overhead).
- **The AMD flag set is Strix-Halo-specific and wrong for a small discrete card.** `COMFYUI_ARGS` replaces it wholesale rather than forcing a rebuild.
- **`TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`**: enables AOTriton kernels for gfx1151 — required for good performance.
- **`TORCH_BLAS_PREFER_HIPBLASLT=1`**: enables recent hipBLASLt improvements for gfx1151 (ROCm/rocm-libraries#3913, #3879).
- **`HSA_ENABLE_SDMA=0`**: disables SDMA engine; improves stability on AMD consumer GPUs.
- **MIOpen first-run slowness**: first generation takes ~2× longer while MIOpen compiles GPU kernels. Cache persists at `~/.cache/miopen` across runs.
- **base image size**: `rocm/pytorch` images are 15–20 GB. Build + pull time is significant.
- **rocm/pytorch image version**: `ROCM_BASE` is a build arg, so a newer tag can be tried without editing the Dockerfile. Newer tags exist (`rocm7.14_*`) but 7.2.4 is the one confirmed working on gfx1151 here — don't bump it blind.
- **pip install during build**: `pip install -r requirements.txt` skips torch/torchvision/torchaudio because they are already satisfied by the stage's PyTorch.
