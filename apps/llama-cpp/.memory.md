## llama-cpp

llama.cpp LLM inference engine, built for one of three GPU runtimes chosen at setup time — ROCm 7.2.4, ROCm 10.0, or NVIDIA CUDA 12.8 — with the Vulkan backend compiled into every variant. Provides fast C++ inference for GGUF models with no Python/PyTorch dependency at runtime. Exports three commands: `llama` (dispatcher), `llama-cli` (direct inference binary), and `llama-server` (direct HTTP API binary).

## Implementation

**GPU runtime picker** (`wizard/00-gpu.runtime`, added 2026-09-13): `arg|LLAMA_GPU`, items `ROCm 7.2|rocm` (default), `ROCm 10.0|rocm10`, `NVIDIA (CUDA)|cuda`. Applicable to `setup,build,create`, so one answer drives both the image (`--build-arg LLAMA_GPU=`) and `create_flags.<value>` — the comfyui/vllm pattern.
- `create_flags.cuda` swaps `/dev/kfd` for CDI `--device nvidia.com/gpu=all` (copy of comfyui's `create_flags.nvidia`). There is deliberately no `create_flags.rocm10`: `cmd_create` falls back to the plain `create_flags` when the variant file is missing, and ROCm 10 needs exactly the ROCm 7 flags.
- The value is `cuda`, not `nvidia` as in comfyui/vllm, because it names the stack alongside `rocm`/`rocm10`. Nothing shared depends on the spelling.

**Base images** — unlike comfyui/vllm, both the build *and* runtime stages depend on the runtime, so the Dockerfile has per-variant stages on both sides and picks with `FROM toolchain-${LLAMA_GPU} AS build` and `FROM runtime-${LLAMA_GPU}`:

| `LLAMA_GPU` | toolchain (build) | runtime |
|---|---|---|
| `rocm` (default) | `rocm/dev-ubuntu-24.04:7.2.4-complete` | same + `mesa-vulkan-drivers` |
| `rocm10` | `rocm/dev-ubuntu-24.04:10.0.0-full` (note `-full`, not `-complete`) | same + `mesa-vulkan-drivers` |
| `cuda` | `nvidia/cuda:12.8.1-devel-ubuntu24.04` + gcc-14 (as upstream's `.devops/cuda.Dockerfile`) | `nvidia/cuda:12.8.1-runtime-ubuntu24.04`, no Mesa |

- All image refs are build args (`ROCM_IMAGE`, `ROCM10_IMAGE`, `CUDA_DEVEL_IMAGE`, `CUDA_RUNTIME_IMAGE`) declared before the first `FROM`.
- The cmake step is one `RUN` with a `case "$LLAMA_GPU"` that `set --`s the backend flags; everything else (Vulkan, `GGML_BACKEND_DL`, CPU variants, build number) is shared. An unknown value fails the build loudly.
- CUDA: `-DGGML_NATIVE=OFF -DCMAKE_EXE_LINKER_FLAGS=-Wl,--allow-shlib-undefined` (libcuda.so.1 is only a stub in the devel image). `CUDA_DOCKER_ARCH` (default `default` = ggml's own list) mirrors `ROCM_DOCKER_ARCH` for fast test builds.
- Vulkan runtime packages are installed per runtime stage, not in the common stage: ROCm stages take `libvulkan1 mesa-vulkan-drivers vulkan-tools`; the CUDA stage takes `libvulkan1 vulkan-tools` with `--no-install-recommends` and no Mesa — NVIDIA's Vulkan ICD comes from the host driver through the CDI spec, and Mesa would only add a CPU (llvmpipe) Vulkan device.
- The `rocm10` runtime stage writes `/etc/ld.so.conf.d/rocm.conf` (`/opt/rocm/lib`) + `ldconfig` — see pitfalls.
- `/etc/llama-cpp-gpu` records the variant, like `/etc/comfyui-gpu` / `/etc/vllm-gpu`.

**Multi-stage build** (required — llama.cpp must be compiled from source):
- Build stage resolves the latest upstream release tag (`b####`) via `git ls-remote` at build time, then shallow-clones that tag and compiles with HIP and Vulkan. llama.cpp cuts a release for virtually every master commit, so "latest release" ≈ master HEAD, but the build is now a deliberate, identifiable version.
- The tag number is passed to cmake as `-DLLAMA_BUILD_NUMBER` (via `/src/.build-number`) so `--version` reports the real release number — a bare `--depth 1` clone reports `version: 1` because llama.cpp derives the build number from `git rev-list --count HEAD`.
- The tag-resolution layer re-runs on every rebuild because `tools.sh` (`cmd_build`) passes a fresh `CACHE_BUST=$(date +%s)` build arg, consumed just before the clone step. Without it, Podman's layer cache would pin the clone forever. Apt layers above stay cached.
- **Release picker wizard**: `wizard/01-release.buildarg` (was `00-` before the runtime page took that slot) (new `.buildarg` wizard type in `lib/wizard.sh`) shows a radiolist of the 10 latest release tags during interactive `tools setup`/TUI; the choice is passed as `--build-arg LLAMA_REF=b####`. Non-interactive setup skips the wizard and `LLAMA_REF` defaults to `latest`. The tags come from `git ls-remote` (sorted numerically — the releases API returns them in publish order, which is the same thing here, but the sort is what guarantees it), so the page keeps its items-cmd and adds `notes-repo|ggml-org/llama.cpp` for the notes. The tags are release tags verbatim, so no `%s` template is needed. llama.cpp marks nearly every release as a pre-release, which the picker shows next to the date — that is upstream's labelling, not a problem with the build.
- CMake flags (ROCm): `-DGGML_HIP=ON -DGGML_VULKAN=ON -DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON`. `-DGGML_HIP_ROCWMMA_FATTN=ON` was dropped with the runtime picker: upstream no longer has that option (not in `ggml/CMakeLists.txt` or `ggml-hip/CMakeLists.txt` at b10948), so it had been a silently ignored cache variable for some time.
- Fat arch target: all gfx architectures including gfx1151 (Strix Halo).
- Vulkan backend needs `libvulkan-dev` + `glslc` (shaderc, Ubuntu universe) + `spirv-headers` at build time; `libvulkan1` + `mesa-vulkan-drivers` at runtime (`vulkan-tools` added for `vulkaninfo` debugging).

**Backend selection**: with `GGML_BACKEND_DL`, each backend is a plugin (`libggml-hip.so` or `libggml-cuda.so`, `libggml-vulkan.so`, CPU variants) loaded at startup, so the same physical GPU appears as two devices — `ROCm0`/`CUDA0` and `Vulkan0`. Users pick per-run with `--device ROCm0` / `--device Vulkan0` on `llama-cli`/`llama-server`; `--list-devices` enumerates. Without `--device`, backend priority puts ROCm first. Vulkan only needs `/dev/dri`; ROCm needs `/dev/kfd` too (both already in `create_flags`).
- Staged artifacts: `build/bin/*` → `/stage/bin/`, `*.so*` → `/stage/lib/`, `.devops/tools.sh` → `/stage/bin/llama-tools`, `convert_hf_to_gguf.py` → `/stage/bin/`, `gguf-py/` → `/stage/gguf-py/`.

**Runtime layout** — everything lands in `/opt/llama-cpp/`:
- Binaries and `.so` backend plugins co-located (required for `GGML_BACKEND_DL` dynamic loading).
- `llama-tools` (upstream `tools.sh`) lives alongside binaries so its relative paths (`./llama-cli`, `./llama-server`, etc.) resolve correctly.
- `gguf-py/` installed in-place via `pip install --break-system-packages -e`.

**Exported commands** (in `/usr/bin/` for `command -pv` compatibility):
- `llama` — `cd /opt/llama-cpp && exec ./llama-tools "$@"`: dispatcher covering `--run/-r`, `--server/-s`, `--quantize/-q`, `--convert/-c`, `--bench/-b`.
- `llama-cli` — passthrough to `/opt/llama-cpp/llama-cli`.
- `llama-server` — passthrough to `/opt/llama-cpp/llama-server`.
- `llama-bench` — passthrough to `/opt/llama-cpp/llama-bench`.

**Model storage**: GGUF files referenced via path; no default location enforced. Distrobox shared `$HOME` means any host path works directly.

## Usage

```bash
# Interactive chat
llama -r -m ~/models/model.gguf
llama-cli -m ~/models/model.gguf

# HTTP API server
llama -s -m ~/models/model.gguf --port 8080
llama-server -m ~/models/model.gguf --host 0.0.0.0 --port 8080

# Quantize a model
llama -q input.gguf output-q4_0.gguf q4_0

# Convert HuggingFace model to GGUF (requires model downloaded locally)
llama -c --outtype f16 ~/models/my-hf-model/

# Benchmark
llama -b -m ~/models/model.gguf
```

## Pitfalls and notes

- **`libllama-*-impl.so` not found**: llama.cpp splits binaries into impl shared libs (e.g. `libllama-cli-impl.so`). The ELF dynamic linker does not search the binary's directory — `/opt/llama-cpp` must be registered via `/etc/ld.so.conf.d/llama-cpp.conf` + `ldconfig`. The `cd /opt/llama-cpp` trick in the `llama` wrapper only helps `GGML_BACKEND_DL`'s `dlopen`, not `ld.so`.
- **`GGML_BACKEND_DL` co-location**: With `-DGGML_BACKEND_DL=ON`, the runtime searches for backend `.so` files in the same directory as the binary. All `.so` files must be in `/opt/llama-cpp/` alongside the binaries — do not split them.
- **`tools.sh` relative paths**: Upstream `tools.sh` calls `./llama-cli`, `./llama-server`, etc. with relative paths. The `llama` shim does `cd /opt/llama-cpp` first; omitting this will fail with "command not found".
- **`--convert` minimal deps**: Only `gguf-py` is installed. Converting from HuggingFace checkpoints that need `torch`/`transformers` requires installing those inside the container at runtime: `pip install --break-system-packages torch transformers sentencepiece`.
- **`git` missing from runtime stage**: The build stage installs `git` (for cloning llama.cpp) but the runtime stage originally didn't. Without it, zsh startup scripts that call `git config` (e.g. delta integration) print "command not found" on every shell entry. `git` is now installed in the runtime stage.
- **`--cap-add SYS_PTRACE` not needed**: Unlike vllm (PyTorch internals), llama.cpp is pure C++ and does not require this capability.
- **Build time**: ~10–20 minutes. Fat arch build compiles ROCm kernels for all listed architectures.
- **Renamed twice**: `llama-cpp` → `llama-cpp-rocm` (July 2026) to carry the GPU stack in the name, then back to `llama-cpp` (September 2026) when the CUDA runtime made `-rocm` wrong. `renamed-from` now says `llama-cpp-rocm`, so the next setup removes that box/image. Container-internal paths (`/opt/llama-cpp/`) and exported command names are unchanged throughout. The Go tests (`tui/wizard_test.go`, `tui/wizardui_test.go`) load this app's real wizard pages by name.
- **ROCm versions pinned**: `ROCM_IMAGE` / `ROCM10_IMAGE` build args at the top of the Dockerfile. Each image is used for both its toolchain and runtime stage, so a bump is one line.
- **One runtime per install**: the box and image names come from the app name, so ROCm and CUDA (or ROCm 7 and 10) builds cannot coexist; switching is a full `tools setup llama-cpp`. A non-interactive CUDA install needs both `BUILD_ARGS` (`LLAMA_GPU=cuda`) and `VARIANT="cuda"` in the state file — the build arg alone creates the box with AMD flags and no GPU.
- **ROCm 10.0 image registers no ROCm libraries with ld.so.** TheRock's own binaries find each other by RPATH (`$ORIGIN/../lib`), and `/etc/ld.so.conf.d/` has only the stock Ubuntu entries (7.2.4 ships one for `/opt/rocm-7.2.4/lib`). Our `libggml-hip.so` carries only the build-tree RUNPATH (`/src/build/bin`), so without the `rocm.conf` entry `ldd` shows `libhipblas.so.3`, `librocblas.so.5`, `libamdhip64.so.7` "not found" — and the failure is silent: the HIP plugin just doesn't load, `--list-devices` shows only `Vulkan0`, and everything still "works" on Vulkan. `/opt/rocm/lib` holds only ROCm libraries plus an OpenCL ICD loader, so registering it shadows nothing from the base OS.
- **`libvulkan1` recommends `mesa-vulkan-drivers`.** A plain `apt-get install libvulkan1` in the CUDA stage pulled Mesa in anyway (caught by `dpkg -l` on the first CUDA build). Hence `--no-install-recommends` there.
- **Testing an image with plain `podman run`**: rootless podman needs `--group-add keep-groups` for `/dev/kfd`. With numeric `--group-add 44 --group-add 992` (what `create_flags` uses under Distrobox) a bare `podman run` reports `failed to initialize ROCm: no ROCm-capable device` while Vulkan still works — easy to misread as a broken build. The old image behaves identically, so it is the invocation. HF-cache GGUFs are absolute symlinks into `blobs/`; mount the resolved blob (`readlink -f`), not the snapshot directory.
- **Verified 2026-09-13** (b10948, test builds with `ROCM_DOCKER_ARCH=gfx1151` / `CUDA_DOCKER_ARCH=89`, not the fat default lists): all three variants build. `llama-bench` on Qwen3.5-9B UD-IQ2_XXS, `-ngl 99 -p 512 -n 64 -r 2`, Radeon 8060S:

  | runtime | ROCm0 pp512 | ROCm0 tg64 | Vulkan0 pp512 | Vulkan0 tg64 |
  |---|---|---|---|---|
  | `rocm` (7.2.4) | 955 | 39.9 | 859 | 50.4 |
  | `rocm10` (10.0.0) | 1075 | 40.5 | 930 | 57.8 |

  One short run each, back to back — enough to say ROCm 10 is not a regression, not enough to call the Vulkan difference (the Mesa version is the same in both) real. Vulkan's tg lead over ROCm on this model holds in both.
- **CUDA variant has never run on NVIDIA hardware** — this host has no NVIDIA GPU. That NVIDIA Vulkan works depends on the host's CDI spec mounting the Vulkan ICD JSON and libraries; recent `nvidia-ctk cdi generate` does, but it was not checked here.
- **Vulkan device missing from `--list-devices`**: check `vulkaninfo --summary` inside the box — if RADV doesn't see the GPU, the problem is `/dev/dri` access (groups/devices in `create_flags`), not llama.cpp. On Strix Halo, Vulkan is a useful fallback when ROCm hangs (`HSA_ENABLE_SDMA=0` only affects the ROCm backend).
- **`spirv-headers` required for Vulkan build**: ggml-vulkan's CMakeLists does `find_package(SPIRV-Headers)` — `libvulkan-dev` + `glslc` alone fail with "Could not find SPIRV-Headers". The noble package ships the needed cmake config. cmake also reports "missing components: glslangValidator" — benign, upstream doesn't install glslang-tools either.
- **`llama-completion` in tools.sh**: Upstream `tools.sh` has a `--run-legacy / -l` branch that calls `./llama-completion`. This binary may not exist in all builds — the flag will error if used.
