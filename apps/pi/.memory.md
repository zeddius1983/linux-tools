## pi

Pi (https://pi.dev, repo `earendil-works/pi`, formerly Mario Zechner's `pi-mono`) is a minimal, extensible terminal coding agent. Packaged as a Distrobox container so it can be exported to the host shell and app menu without a host Node install.

## Implementation

- **Base image**: `docker.io/ubuntu:24.04` + NodeSource Node 24 (Pi needs Node >= 22.19; Ubuntu ships 18). npm stays in the image because Pi runs it at runtime for `pi install npm:...`
- **Install method**: `npm install -g --ignore-scripts @earendil-works/pi-coding-agent@<version>`, upstream's documented npm route (no lifecycle scripts needed). Not the `pi.dev/install.sh` installer, which installs into `$HOME` and would land on the shared home
- **Release picker**: `wizard/00-release.buildarg` is a `releases|earendil-works/pi` page → build arg `PI_RELEASE` (tag such as `v1.4.0`; the `v` is stripped for npm). `latest` is npm's dist-tag. `CACHE_BUST` forces the install layer to rerun each build
- **Launcher** `apps/pi/pi` → `/usr/bin/pi`: npm's shim is removed and replaced by `exec /usr/bin/node <entrypoint>`, the entrypoint path recorded from the shim at build time into `/usr/lib/pi/entrypoint`. Same fix as openclaw-bin
- **Exports**: `bin:pi` and `desktop:pi:Pi` (terminal-launched menu entry)
- `git`, `ripgrep`, `gh`, `curl` in the image
- **Icon** `icon.svg`: Pi's mark from `pi.dev/favicon.svg` (three paths, 560×560 viewBox), drawn `#f6f6f6` on a rounded `#111111` tile. The upstream favicon is a bare black mark that flips colour via a `prefers-color-scheme` media query in its `<style>`, which desktop icon renderers ignore, so as-is it would vanish on dark panels

## Pitfalls and notes

- **`#!/usr/bin/env node` trap**: `~/.local/bin` (shared home) precedes `/usr/bin`, and dev-toolbox exports `node` there, so npm's own shim would re-enter dev-toolbox-box, where Pi's files don't exist. Hence the launcher naming `/usr/bin/node`
- **…and the same for Pi's subprocesses**: `pi install npm:...` runs `npm` from PATH, and dev-toolbox exports `npm`/`npx` to `~/.local/bin` too, so package installs would run in dev-toolbox-box (and npm's own `env node` shim could pick up a foreign Node). Pinning the interpreter alone didn't cover it (caught in PR review). The launcher now does `export PATH="/usr/bin:$PATH"` before exec; side effect is that bash commands Pi runs prefer the box's tools over same-named host exports
- **`pi update` (self-update) doesn't work here**: it would `npm install -g` into `/usr`, owned by root in the image and replaced on rebuild. Update with `tools setup pi`. `pi update --extensions` is fine (packages live under `~/.pi/agent/`)
- Everything user-side is in `~/.pi/agent/` (settings, credentials, sessions, packages), so it survives rebuilds
- No permission prompts upstream, by design; the README warns that the box shares `$HOME`
- Builds only through `tools` (needs the `distrobox-deps` build context)
- **Installed release is recorded** (2026-10-31) at `/usr/share/linux-tools/release` for the dashboard's update check (see "Release pickers record what they installed" in `CLAUDE.md`): `version` from the installed `@earendil-works/pi-coding-agent/package.json`, prefixed with `v`.
