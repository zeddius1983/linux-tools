## gputaskman

Terminal GPU task manager (per-process VRAM, engine load, LLM weights / KV cache)
from upstream's portable Linux release. The box carries the picked release, but
the program runs on the host, because its process table is unreadable from a box.

## Implementation

- **Base image:** `docker.io/ubuntu:24.04`, only for curl, git and the distrobox
  dependencies. The app is a self-contained PyInstaller bundle in `/opt/gputaskman`.
- **Release picker:** `wizard/00-release.buildarg`, `GPUTASKMAN_RELEASE`, tags like
  `v0.3.5` or the default `latest`. `latest` comes from the `releases/latest`
  redirect (no API rate limit). The tarball is checked against upstream's `.sha256`.
  `tag-match|` excludes `v0.1.0`, which has no Linux asset.
- **Release file:** taken from `_internal/gputaskman-<ver>.dist-info`, since the CLI
  has no `--version`.
- **Launcher (`apps/gputaskman/gputaskman`):** copies the bundle to
  `~/.local/share/gputaskman/<release>/` once per release (staged, then renamed;
  other releases pruned), then `exec distrobox-host-exec` on it.
- **Exports:** `bin:gputaskman` and `desktop:gputaskman:gputaskman`. No `gtm` alias.
  `description` is just the app name, by choice: it also labels the box's terminal
  shortcut in the application menu.
- **`host-paths`:** lists the host copy, so `tools rm` deletes it. `tools setup`
  does not; the launcher prunes old releases itself.
- **No `create_flags` and no GPU wizard page:** it runs on the host, so `/dev/dri`
  passthrough and NVIDIA CDI don't apply.

## Pitfalls and notes

- **Why not simply run in the box, like nvtop and amdgpu_top?** GPU hardware is
  reachable from a box, but this app's core feature is the per-process table from
  `/proc/<pid>/{fd,fdinfo,maps}`, and `ptrace_may_access` fails across user
  namespaces. Measured 2026-11-10 with v0.3.5 on Mint 22.3, `amdgpu`:
  - plain `gputaskman-box`, with or without `sudo`: 0 processes; host: 17; device
    totals matched. This was shipped and tried, and rejected for the empty table.
  - `SYS_PTRACE` + `SYS_ADMIN` + seccomp off: 0, with or without `sudo`.
  - `--userns=host`: 0 as the user, 3 with `sudo` (Telegram, orca-ide, Chrome, i.e.
    apps in other boxes, never native host apps).
  The host can read boxed processes, so a host run sees everything.
- **The host cannot run the file in place** via `/proc/<pid>/root/opt/...`: exit
  255, since `/proc/self/exe` reads `/opt/gputaskman/gputaskman` and the bootloader
  looks in the host's `/opt`. Hence the copy.
- **`ls /proc/<pid>/fd` succeeds from a box even when denied in practice;** it is
  `readlink` on the entries that fails. Don't use a directory listing as a probe.
- **Host reachability is tested by output, not exit status.** Without the host's
  `flatpak` package `distrobox-host-exec` silently returns nothing, and the first
  call in a new box only bootstraps host-spawn, hence the retry. `--yes` stops the
  bootstrap prompt from swallowing the probe. If unreachable, the launcher warns
  and runs the bundle in the box.
- **Closing the terminal orphans the process; `q` does not.** The `podman exec`
  session survives its client, so the box-side chain stays up and keeps the host
  process alive. `nvtop` tested identically, so it is Distrobox behaviour and not
  fixed per app.
- **`pkill -f` patterns run from a box see the calling shell too:** PID namespaces
  are shared. Anchor with `^`, or the test kills its own shell.
- **Flags differ between releases:** `--no-system` exists in v0.3.5 but not v0.3.4.
- Upstream is alpha and releases often. Tested on v0.3.4 and v0.3.5 with AMD only;
  the NVIDIA and Intel paths have not been run through this packaging.
- `tools` on this host is a release install; test a checkout with `./tools.sh`.
