## gpu-unlock

Container build environment and exported `gpu_unlock` controller for Zagitta's
early-boot tensor-throughput unlock. Kernel compilation, firmware generation and
CUDA PyTorch stay in the image; host writes install artifacts and boot integration.

## Implementation

- Description `gpu-unlock`, `bin:gpu_unlock`; paired Ubuntu 24.04 / rolling Arch
  Dockerfiles. Source pin `6081407b312aa3139a2bed62bdda354f4ffddc1d` (1.1.0).
  image-setup verifies both NVIDIA 610.43.03 input SHA256s and generates firmware.
- uv 0.9.5, managed Python 3.12.12, PyTorch 2.8.0 CUDA 12.8, NumPy 2.2.6. CDI
  passthrough; Mesa preinstalled in Arch before CDI injects libGLX_indirect.so.0,
  avoiding first-start pacman conflicts. Expensive setup precedes final copies.
- `gpu_unlock install [KERNEL] [--initramfs TOOL] [--keep-build]` runs the compiler
  against read-only host headers. Clang/LLVM selected from kernel .config.
  Missing objtool libraries are staged from host distro/multiarch directories;
  a named unresolved library fails immediately before compilation.
- Workspaces under shared-home builds/ are cleaned by an EXIT trap on success
  and failure. --keep-build opts into retaining them. Older build folders are not
  automatically deleted.
- common.sh owns the single host handoff used by build and control commands.
  Privileged actions tar the helper + install payload, compute SHA256 before the
  password prompt, pass bootstrap code and digest as sudo argv, and verify a
  root-owned /var/tmp snapshot before extracting or executing anything. The
  module and helper used by root are read only from that private verified tree.
  Both shared-home transfer data and root snapshots have EXIT cleanup traps.
  Status is read-only: code passed as a bash argument, no home executable/sudo.
- host-bootstrap extracts with --no-same-owner/--no-same-permissions and rejects
  symlinks/special files. This binds the authorized bundle across the sudo prompt
  and closes replacement of the user-owned helper/module/archive during that
  interval. It does not claim to secure an already-compromised build toolchain.
- Host helper creates fresh app-specific firmware/license trees with explicit
  root:root ownership, 0755 directories and 0644 regular files. It never copies
  source directory metadata onto shared firmware/license parents. Boot scripts
  and modules use explicit owner/group/modes too.
- Native module under /lib/modules/KERNEL/updates/linux-tools-gpu-unlock; no DKMS.
  Rebuild after kernel upgrades. Installed-kernel markers and selected backend
  under /var/lib/linux-tools/gpu-unlock, readable but not writable by the user.
- Auto backend selection uses recorded state first, then kernel-install's
  explicit generator, then a single available tool. Multiple tools or config
  drop-ins require --initramfs dracut|mkinitcpio|update-initramfs. Persist it and
  reuse it for toggles/removal. Never choose by installed-command priority.
- on/off write an empty/all/full-PCI-list module parameter and regenerate images;
  reboot required, no hot resets. Failed rebuild restores old request and retries
  regeneration. Explicit aggregate status preserves multi-kernel failures.
- mkinitcpio MODULES ordering/FILES; initramfs-tools init-top loader before udev;
  dracut auto-including module with a pre-udev hook. Dracut check() skips kernels
  lacking a compiled module; no forced add_dracutmodules config is created.
- Uninstall bypasses legacy-argument/DKMS conflicts, removes own modules/hooks,
  preserves shared firmware used by a separate DKMS install, and explains legacy
  settings separately. It never deletes the unowned dracut .conf path. Explicit
  --initramfs also permits removing older installs with no recorded backend.
- Benchmarks: FP16/BF16/TF32 GEMM, CUDA events, repeated medians, finite checks,
  CPU FP64 spot checks, saved JSON and comparison with metadata validation.

## Pitfalls and notes

- Active PCI table at this pin only enables selected GA102/GA103/GA104/GA106 IDs,
  despite upstream README wording about GA100 and RTX 4090.
- Old native packages/boot arguments block install/on/off, not uninstall.
- Explicit mkinitcpio -c/_config or dracut module allowlists need manual inclusion
  of the integration. Backend selection identifies a tool, not proof of a booted
  GPU unlock; verify kernel logs after reboot. Enforced Secure Boot signing/key
  enrollment is not automated.
- host-bootstrap runs under umask 077 to keep its snapshot private. The helper's
  privileged main() resets umask 022 before acting; otherwise depmod writes
  root-only modules.dep* indexes (breaking unprivileged modinfo) and mkdir -p
  creates 0700 system directories such as Ubuntu's missing /usr/share/licenses.
  sudo can also impose a strict umask of its own, so do not rely on the caller.
- No sudo stderr suppression or sudoers additions. No code paths into versioned
  linux-tools trees. ROOT='' is fixed in host helper; tests override it only after
  sourcing. Root tests use fake system roots inside a disposable container/CI.
- Tests cover malicious source ownership/modes, preservation of shared parents,
  root-owned snapshot execution, replaced module/archive refusal, backend
  ambiguity/config/persistence, toggle rollback, uninstall with legacy conflicts,
  unowned config preservation, transfer cleanup and Ubuntu multiarch objtool libs.
- Review validation: root ownership/bootstrap/backend/controller regressions
  passed in a disposable container. The actual CachyOS module build and archive
  handoff passed with a host-install stub; success/failure workspace cleanup and
  explicit --keep-build behavior were checked end to end. Shared system parents
  with unsafe ownership/write bits are refused rather than silently trusted.
- Previously validated Arch image builds, CachyOS 7.3 module compilation with a
  host-install stub, actual dracut image generation in a disposable container,
  and the default benchmark on RTX 3080.
- Real host validation (2026-10-26): CachyOS 7.3.0-4, Limine + limine-mkinitcpio,
  RTX 3080 (10de:2206, display card) on driver 580.178.04. install -> on -> reboot
  logged `gpu_unlock: unlocked` and a clean handoff (ss0 0x88888888, ss1 0x8).
  Benchmark at 320 W: FP16 60.3->106.8, BF16 63.7->109.4, TF32 30.9->52.6 TFLOPS
  (~1.7x), spot-check errors unchanged. CachyOS badge is now tested; Ubuntu/Mint
  stay untested until run there. Unsigned module taints the kernel (expected).
- `gpu_unlock off` + reboot verified on the same host: BF16 throughput returned
  to locked rates. llama.cpp (llama-bench -dev CUDA0 -fa 1, build 620d222),
  Llama 3.2 3B pp512: BF16 7.44k locked -> 11.31k t/s unlocked (1.52x); F16
  ~10.75k t/s both ways (llama.cpp accumulates F16 in FP16, never throttled);
  tg128 ~100 t/s both ways (bandwidth bound). Pin -dev CUDA0: the box loads the
  Vulkan backend too and llama-bench otherwise lists the 3080 twice. Strata's
  DeepSeek expert-streaming setup is I/O bound (~28 t/s prefill) and cannot show
  the unlock; use a VRAM-resident BF16 model to measure LLM gains.
- ComfyUI 0.35.0 SDXL 1024^2 euler (comfy_bench.py via the HTTP API, varying
  seeds to defeat the node cache, per-step = 30-step minus 10-step medians):
  FP16 3.29 -> 4.95 it/s (1.50x), --bf16-unet 2.93 -> 4.51 it/s (1.54x).
  PyTorch FP16 accumulates in FP32, so default ComfyUI benefits. Don't pass
  --fast (fp16_accumulation) when comparing; keep VRAM free of Strata.
- Actual host diagnosis: CachyOS uses limine-mkinitcpio-hook; dracut is absent.
  /usr/bin/update-initramfs is owned by cachyos-hooks and dispatches to the real
  generator, so command presence alone was a false initramfs-tools candidate.
  /usr/local/bin/mkinitcpio is an interactive Limine wrapper; use the active
  hook's limine-mkinitcpio entrypoint to update boot entries (no presets exist).
- Read-only preflight now selects the host backend before creating a workspace
  or compiling. Active Limine pacman hooks respect local/vendor precedence and
  /dev/null masks. Generator mismatches are refused. Plain update-initramfs needs
  actual /usr/share/initramfs-tools integration, not just a compatibility command.
- **distrobox-init's first-start packages are preinstalled** (2026-10-27) through the shared
  `lib/distrobox-deps` step near the top of the Dockerfile.ubuntu, so a fresh box's
  `Installing basic packages...` is a no-op instead of a ~250-package download (see
  "Distrobox first-start packages" in `CLAUDE.md`). It builds only through `tools`, which
  passes the `distrobox-deps` build context; a bare `podman build` fails at that `COPY`.
