## corefreq

Packages [CoreFreq](https://github.com/cyring/CoreFreq) (CPU monitor/tuner) as a build-environment container. The kernel module and daemon can't run inside the container itself — the `.ko` has to load into the *host* kernel — so this follows the "build-environment container" pattern from the top-level `CLAUDE.md`: container provides the toolchain, `corefreq-setup` builds at runtime against whatever kernel headers are mounted in from the host, and copies the artifacts to `~/.local/corefreq/` where Distrobox's shared `$HOME` makes them visible on the host.

## Implementation

**Two Dockerfiles, picked by host distro family.** `apps/corefreq/Dockerfile.ubuntu` and `apps/corefreq/Dockerfile.arch` both exist; `lib/commands.sh`'s `cmd_build` detects this pair and builds with `-f Dockerfile.$(host_distro_family)` (`lib/helpers.sh`), where `host_distro_family` greps the *host's* `/etc/os-release` `ID`/`ID_LIKE` for `arch`. This is a generic, opt-in mechanism — any app that ships both files gets picked automatically; apps with a single `Dockerfile` are unaffected. See pitfalls below for why one Dockerfile wasn't enough.

- `Dockerfile.ubuntu`: `ubuntu:24.04` + `build-essential` (GCC) + `dwarves` (pahole's Debian/Ubuntu package name). No Clang — a genuine Ubuntu/Debian-family host's kernel is GCC-built, so none of the Clang workarounds below apply there.
- `Dockerfile.arch`: `archlinux:base-devel` + `clang lld llvm pahole` (pahole's *own* package name on Arch — see pitfalls, this bit us once already). Covers CachyOS and other Arch-family hosts, whose kernels are Clang-built. Needs the full `llvm` package, not just `lld` — Kbuild's `LLVM=1` path calls `llvm-objcopy`/`llvm-ar`/etc. for BTF post-processing, which only `llvm` provides (`lld` is just the linker, `ld.lld`).
- `create_flags` (shared by both): `--privileged -v /usr/src:/usr/src:ro -v /lib/modules:/lib/modules:ro` — Distrobox does not auto-share these, and `/usr/src` is needed for the `/lib/modules/$(uname -r)/build` symlink to resolve.
- `corefreq-setup` (a `bin:` export, wrapper script baked into the image via `printf`, nearly identical between the two Dockerfiles — see pitfalls for the one real difference):
  1. Resolves `KBUILD` from `/lib/modules/$(uname -r)/build` (falls back to `/usr/src/linux-headers-$(uname -r)`).
  2. Copies the CoreFreq source (cloned at image-build time into `/opt/corefreq-src`) to `~/.local/corefreq-build`.
  3. **Arch variant only:** checks `${KBUILD}/.config` for `CONFIG_CC_IS_CLANG=y`; if set, adds `LLVM=1` to the `make` invocation.
  4. Runs `ldd` on the host's prebuilt `${KBUILD}/tools/objtool/objtool`, copies any `not found` shared libraries in from `/run/host/usr/lib` (Distrobox's standard host-root mount), and points `LD_LIBRARY_PATH` at the staged copies before building. Present in **both** variants (see pitfalls).
  5. Runs `make KERNELDIR=...` (plus `LLVM=1` if added).
  6. Installs `corefreqk.ko`, `corefreqd`, `corefreq-cli` into `~/.local/corefreq/` via **temp-file + `mv -f`** (not in-place `cp` — see the "Text file busy" pitfall).
  7. Copies the two baked host-side helper scripts (`module-reload`, `daemon-ensure`) from `/usr/share/corefreq/` into `~/.local/corefreq/` (so they're host-visible via the shared `$HOME`), writes a sudoers file whitelisting exactly `<DEST>/module-reload <DEST>` and `<DEST>/daemon-ensure <DEST>`, installs it with one `distrobox-host-exec sudo install ...` (the only password prompt), then runs `distrobox-host-exec sudo "$DEST/module-reload" "$DEST"` to kill any old daemon, unload the old module, and load the freshly built one.
- **Privileged host operations live in two baked helper scripts**, not inline in the wrappers (`/usr/share/corefreq/{module-reload,daemon-ensure}`, copied to `~/.local/corefreq/` at setup, each taking the install dir as `$1`):
  - `module-reload <DEST>`: kills running `corefreqd` (by `/proc/PID/exe` identity — see pitfalls), `rmmod corefreqk || true`, `insmod`. Used by `corefreq-setup` after a rebuild.
  - `daemon-ensure <DEST>`: `insmod` if `/sys/module/corefreqk` absent, then starts `corefreqd` (via `nohup`) if not already running (same exe-identity check). Used by `corefreq-cli` on every launch — whitelisted in sudoers so it's fully passwordless.
- `corefreq-cli` (a `desktop:` export, byte-identical in both Dockerfiles) just runs `distrobox-host-exec sudo "$DEST/daemon-ensure" "$DEST"` (one passwordless host call) then execs the real `corefreq-cli` binary.
- All host operations go through `distrobox-host-exec` — module load/`pgrep`/`/sys` checks all need real host state, which the container's own process/module namespace doesn't have. **Crucially, anything matching process names by pattern runs *inside* a host-side script**, never as `distrobox-host-exec sudo pkill -f corefreqd` directly — see the pkill-self-match pitfall.

## Pitfalls and notes

- **Why two Dockerfiles instead of one.** The original single `ubuntu:24.04`-based image required three separate, escalating workarounds to build CoreFreq's kernel module against a CachyOS host (see debugging history below): a newer Clang than Ubuntu packages, Kbuild's suffixed `LLVM=-N` mechanism plus runtime version-globbing, and a manually staged `libsframe`. Each fix addressed a real gap, but they all existed only because Ubuntu 24.04 is a fixed 2024 snapshot while CachyOS tracks bleeding-edge everything. An Arch-based image sidesteps the first two entirely: pacman's `clang`/`lld` track vanilla Arch (which CachyOS packages generally lag by days, not years), and pacman never does Debian-style versioned parallel installs, so plain `LLVM=1` just works — no suffix detection needed. `lib/commands.sh`/`lib/helpers.sh` gained a small, generic `Dockerfile.ubuntu` + `Dockerfile.arch` + `host_distro_family()` mechanism (not corefreq-specific) so any future kernel-module-building app can reuse the same pattern instead of accumulating Ubuntu-side workarounds for Arch hosts.
- **CachyOS (and any Clang-built kernel) can't have its module built with GCC.** CachyOS kernels are compiled with Clang and carry Clang-only codegen flags in their build config (retpoline thunks, ThinLTO `-fsplit-lto-unit`, `-fexperimental-late-parse-attributes` for hardening attributes, raw `-mllvm` passthroughs). These flags get baked into the kernel's `Kbuild`/`Makefile.build` invocation regardless of which compiler you point `CC` at, so running `make` with plain GCC fails immediately with `unrecognized command-line option` for each Clang-specific flag — it's not a version-skew warning, it's a hard build failure. `Dockerfile.arch`'s `corefreq-setup` detects this via `CONFIG_CC_IS_CLANG=y` in `${KBUILD}/.config` and adds `LLVM=1` (the standard kernel Kbuild switch, see `Documentation/kbuild/llvm.rst`) only when the host actually needs it — GCC-built kernels are unaffected.
  - `LLVM=1` is passed via `MAKE_ARGS` to CoreFreq's *top-level* `make`, not into its own `$(CC)` variable. CoreFreq's Makefile does `CC ?= cc` and uses that for the userspace `corefreqd`/`corefreq-cli` build, but the kernel module target invokes `$(MAKE) -C $(KERNELDIR) M=... modules` recursively — GNU Make automatically forwards command-line-origin variables (like `LLVM=1`) to that recursive sub-make, so only the module build switches to Clang; the userspace daemon/CLI still build with the container's system GCC, which is fine (no host-ABI concern there).
  - **Historical note (no longer relevant with the Arch base, kept for context):** when this was still one `ubuntu:24.04` image, Ubuntu's packaged `clang-18` was too old — `-fexperimental-late-parse-attributes` needs Clang 19+. Pulling a current Clang from `apt.llvm.org` worked, but since that installs versioned binaries only (`clang-22`, no unversioned symlink), it required Kbuild's suffixed form (`LLVM=-22`) plus a runtime `ls /usr/bin/clang-[0-9]* | sort -V | tail -1` to discover the installed version. The Arch base's single unversioned `clang` makes all of that unnecessary — hence plain `LLVM=1` in `Dockerfile.arch`.
  - Debugging progression on a CachyOS host, in order: (1) GCC → `unrecognized command-line option '-mstack-alignment=8'` etc.; (2) Ubuntu's `clang-18` + `LLVM=1` → `unknown argument: '-fexperimental-late-parse-attributes'`; (3) `apt.llvm.org`'s Clang 22 + suffixed `LLVM=-22` → compiled and linked; (4) switched the whole approach to an Arch base instead of continuing to patch Ubuntu, once a *third*, unrelated gap (missing `pahole`, see below) showed the pattern was systemic rather than a one-off.

- **The kernel headers ship a prebuilt `tools/objtool/objtool` binary tied to the *host's* binutils, not the container's.** Even with the Clang mismatch fixed, `corefreqk.o` compiles and links fine, but the `objtool` ORC/stack-validation pass can still fail: `error while loading shared libraries: libsframe.so.3: cannot open shared object file`. This binary was built ahead of time (as part of the kernel-headers package) against the host's own binutils/libsframe (a small library for the SFrame stack-trace format), whose SONAME can be newer than whatever the container's distro packages. Since `/lib/modules` and `/usr/src` are mounted **read-only** (`create_flags`), Kbuild can't just rebuild `objtool` from source inside the container — it's stuck using the host's binary as-is.
  - Fix: don't try to package-install a matching libsframe version (there's no guarantee any distro's repos carry the exact SONAME a rolling-release host needs). Instead, reuse the actual host library via Distrobox's own `/run/host/` mount, which exposes the entire host root filesystem read-only inside **every** Distrobox container by default — no extra `create_flags` needed for this part. `corefreq-setup` runs `ldd` on the prebuilt `objtool`, and for each `not found` library, copies it (via `cp -L`, dereferencing the symlink to get the real file, e.g. `/run/host/usr/lib/libsframe.so.3 -> libsframe.so.3.0.0`) from `/run/host/usr/lib` (falling back to `/run/host/usr/lib64`, `/run/host/lib`) into a small scratch dir `~/.local/corefreq-libs/`, then prepends that dir to `LD_LIBRARY_PATH` only when something was actually missing.
  - Deliberately scoped to a small staging directory rather than adding all of `/run/host/usr/lib` to `LD_LIBRARY_PATH` — blanket-exposing the host's entire lib tree risks shadowing the container's own glibc/libstdc++/etc. with host copies for every process the build spawns (gcc, ld, make, ...), which could silently break the build in more confusing ways than the original missing-library error.
  - This check is present in **both** Dockerfiles and not gated on Clang detection — it's a generic, self-healing fix for a container-vs-host binutils version gap, which is orthogonal to the compiler question and could in principle hit a GCC-built rolling-release kernel too.

- **`pahole` isn't just an Arch/CachyOS thing, and its package name differs by distro.** The third gap hit while debugging this: `pahole: not found` during the BTF-encoding step (`gen-btf.sh`). This is needed whenever the host kernel has `CONFIG_DEBUG_INFO_BTF=y`, which is also true of **stock Ubuntu kernels** — it's unrelated to the Clang/objtool issues above. Debian/Ubuntu packages it as `dwarves`; Arch packages it as `pahole` directly — there is no `dwarves` package on Arch (`pacman -S dwarves` → `error: target not found: dwarves`). Both `Dockerfile.ubuntu` and `Dockerfile.arch` install it under the correct name for their distro.
  - **This exact typo (`dwarves` in `Dockerfile.arch`) shipped once and silently built a broken image.** `pacman -S`'s behavior on an unresolvable target is to abort the *entire* transaction — not just skip that one package — so `clang lld pahole git ca-certificates kmod sudo` all failed to install, not just the mistyped one. The `RUN` line's trailing `&& yes | pacman -Scc --noconfirm >/dev/null 2>&1 || true` masked this: `cmd1 && cmd2 || true` groups as `(cmd1 && cmd2) || true`, so a failing `cmd1` (the install) falls through to `|| true` exactly the same as a failing `cmd2` would, and the Dockerfile step reported success. The build only failed two steps later, on an unrelated `git: command not found`, once things had already gone this far off the rails. Fixed by wrapping only the best-effort cache-clean in its own `|| true`: `pacman -Syu ... && (yes | pacman -Scc --noconfirm >/dev/null 2>&1 || true)`.

- **`distrobox-host-exec` needs `curl` or `wget` in the container to bootstrap itself on a fresh box.** `distrobox-host-exec` (the script Distrobox ships in every container) depends on a separate helper binary, `host-spawn`, to actually reach the host. If `host-spawn` isn't already present — true for any brand-new box, since it's installed *inside* the container's own filesystem, not shared via `$HOME` — the script tries to download it from GitHub using `curl` or `wget`, whichever it finds first (`download_command` in `/usr/bin/distrobox-host-exec`). Neither `Dockerfile.ubuntu` nor `Dockerfile.arch` originally installed either one, so on a fresh Arch-based `corefreq-box`, `corefreq-cli`'s very first `distrobox-host-exec sudo insmod ...` call hit this: `download_command` stayed empty, the download step failed, and because the surrounding script runs under `set -o errexit`, it exited early — with the failure easy to miss in a terminal, since `corefreq-cli`'s own `set -euo pipefail` wrapper then aborted immediately too, right after printing "Loading corefreqk...".
  - Symptom: `corefreq-cli` prints `==> Loading corefreqk...` then returns straight to the shell prompt with no module loaded and no further output; `dmesg` shows *no* attempt to load `corefreqk` at all (confirming it never reached the kernel — the failure was in `distrobox-host-exec`/`host-spawn`, not `insmod` itself). Secure Boot / module signing is a red herring here; check `dmesg` before chasing that.
  - Fix: install `curl` in both Dockerfiles. This is a Distrobox-tooling dependency, not specific to CoreFreq or either distro family — any minimal/from-scratch base image is exposed to it the first time an app in this repo calls `distrobox-host-exec`.

- **The daemon/module lifecycle went through a whole minefield before landing on the two-helper-script design.** Once `distrobox-host-exec` actually worked (flatpak installed), re-running `corefreq-setup` surfaced four distinct, interacting problems. The final design (baked `module-reload`/`daemon-ensure` scripts, copied to `$DEST`, invoked via one `distrobox-host-exec sudo "$DEST/<script>" "$DEST"` each) exists specifically to dodge all four at once. The problems, and why the design beats the naive inline approach:
  1. **`Text file busy` on binary overwrite.** In-place `cp` over `~/.local/corefreq/corefreqd` fails while a copy is running (Linux blocks writing a mapped/running executable, `ETXTBSY`). Fix: install via temp-file + `mv -f` — renaming over a running binary succeeds because the old process keeps the old inode; the new file gets a new inode. This *removes the need to stop the daemon before installing binaries at all*.
  2. **`pkill -f corefreqd` self-terminates when invoked as `distrobox-host-exec sudo pkill -f corefreqd`.** `-f` matches the full command line, and the `sudo pkill -f corefreqd` process's *own* cmdline contains the string "corefreqd" → pkill kills its own sudo/host-spawn wrapper (observed as `Terminated  distrobox-host-exec sudo pkill -f corefreqd`), racily, often before signalling all the real daemons. Running the kill *inside a host-side script* fixes this: the wrapper process is then `bash $DEST/module-reload $DEST`, whose cmdline does **not** contain "corefreqd", so `pgrep -f corefreqd` in the script matches only the real daemons.
  3. **`pgrep -x corefreqd` never matches — CoreFreq renames its workers.** `corefreqd` forks and `prctl(PR_SET_NAME)`s its children to `corefreqd-pmgr`/`corefreqd-cmgr` (confirmed via `sudo fuser -v ~/.local/corefreq/corefreqd`). `-x` (exact match on `/proc/PID/comm`) therefore finds nothing even while it's running — which first looked like a host-spawn visibility bug (red herring; `ps aux` on the host showed them fine). The helper scripts match on **`/proc/PID/exe` identity** instead (`readlink /proc/$pid/exe` equals `$DEST/corefreqd`, or `"$DEST/corefreqd "*` to also match the `(deleted)` suffix after a rename-install) — robust against both the renaming *and* self-match, and version-independent (doesn't hardcode the `-pmgr`/`-cmgr` names).
  4. **`sudo`'s credential cache doesn't carry across separate `distrobox-host-exec` calls.** A single setup run prompted for the password three times in a row; each `distrobox-host-exec` goes through `host-spawn`'s D-Bus `HostCommand` as a fresh host-side session, not inheriting the terminal's sudo timestamp. Two consequences baked into the design: (a) collapse the privileged sequence into **one** host-side script per phase (`module-reload` for setup, `daemon-ensure` for the CLI) so there's at most one prompt; (b) **never** put `2>/dev/null` on a `distrobox-host-exec sudo ...` call — it hides the password prompt itself, not just noise, silently no-op'ing the command (this is what made an earlier `... rmmod corefreqk 2>/dev/null ...` leave the old module loaded → `insmod: File exists`). The `daemon-ensure` path the CLI uses every launch is whitelisted in `/etc/sudoers.d/corefreq` with its exact `<DEST>/daemon-ensure <DEST>` invocation, so it's genuinely passwordless; only setup's one-time sudoers `install` prompts.
  - Sudoers arg-matching note: the whitelist lines specify the command **with** the `$DEST` argument (`... NOPASSWD: /home/<user>/.local/corefreq/daemon-ensure /home/<user>/.local/corefreq`). Sudo matches args by glob; the home path has no glob metacharacters so it's a literal match. The scripts take `$DEST` as `$1` (rather than deriving it from `$HOME`) precisely because under `sudo` `$HOME` is root's, not the user's.
  - **`daemon-ensure` must wait for the daemon's shm segment before returning, or the very first CLI launch after a reboot fails.** `corefreqd` publishes its POSIX shared memory (`/dev/shm/corefreq-ro-shm` + `corefreq-rw-shm`) only *after* it finishes initializing, but `daemon-ensure` originally started it with `nohup ... &` and immediately `exit 0`'d, after which `corefreq-cli` `exec`'d straight into the real CLI — which then raced a not-yet-ready daemon and failed to attach. The tell was the "only the first time" symptom: on first launch after a reboot the daemon is started fresh (module just insmod'd, no daemon running), so the race is live; every later launch finds the daemon (and its shm) already up, so `daemon-ensure` returns via the early `exit 0` and the CLI connects fine. Fix: after the `nohup`, poll `[ -e /dev/shm/corefreq-ro-shm ]` up to ~5s (`for _ in $(seq 1 50); do ...; sleep 0.1; done`) before returning. Only the just-started branch pays this wait; the already-running branch still early-exits. Applied identically in both `Dockerfile.arch` and `Dockerfile.ubuntu`.

- **Fully-qualified base images required** (per the top-level `CLAUDE.md` pitfall on unqualified image names): `docker.io/library/ubuntu:24.04` and `docker.io/library/archlinux:base-devel`. Confirmed `base-devel` is an actively maintained official tag (weekly rebuilds) via the Docker Hub API before using it.
