## nvtop

`htop`-style multi-vendor GPU TUI (NVIDIA / AMD / Intel / …) with a per-process
GPU table. Complements the vendor-specific `amdgpu_top` and `nvbandwidth` apps by
showing every GPU in one view. TUI-only → exported as `bin:nvtop` +
`desktop:nvtop` (terminal-launched).

## Implementation

- **Base image:** `registry.fedoraproject.org/fedora:43`. Fedora ships an
  `nvtop` package built with all backends enabled, so a single `dnf install
  nvtop` gets NVIDIA + AMD + Intel support — no source build, no CUDA toolkit.
- **NVIDIA path = NVML dlopen + CDI.** nvtop does not link the NVIDIA driver; its
  NVIDIA backend `dlopen()`s `libnvidia-ml.so.1` at runtime. That lib is injected
  by CDI (`--device nvidia.com/gpu=all`), the same passthrough nvbandwidth uses.
  So no CUDA/driver is needed at image-build time.
- **GPU passthrough is a wizard choice, not a fixed flag** (2026-08-06). The CDI
  flag lives in `create_flags.nvidia`, selected by `wizard/00-gpu.runtime`
  (`AMD / Intel|amd` first = default, `NVIDIA (CDI)|nvidia`). There is
  deliberately **no plain `create_flags` and no `create_flags.amd`**: `cmd_create`
  (`lib/commands.sh`) falls back to `create_flags` when `create_flags.$variant` is
  absent and skips `--additional-flags` entirely when neither exists, so both the
  `amd` variant and the no-wizard path create a box with zero extra flags. Same
  shape as `apps/comfyui`, except comfyui's AMD side does need flags so it keeps a
  plain `create_flags`.
- **AMD/Intel path = default device passthrough.** Those backends read libdrm +
  `/sys/class/drm` / `/dev/dri`, which Distrobox exposes by default — this is why
  the sibling `amdgpu_top` app needs no `create_flags` at all. nvtop inherits the
  same access, so AMD/Intel monitoring works regardless of the NVIDIA flag.
- **Exports:** `bin:nvtop` (host PATH) + `desktop:nvtop:nvtop` (terminal window
  launcher). No `gui:` — it's a curses TUI, not a windowed app. No bundled icon
  (falls back to `utilities-terminal`).

## Pitfalls and notes

- **Host CDI spec is a hard prerequisite** for the `--device nvidia.com/gpu=all`
  flag: needs `/etc/cdi/nvidia.yaml` (`nvidia-ctk cdi generate`). Missing → podman
  `no such device nvidia.com/gpu=all` at create time. Regenerate after driver
  updates. Do NOT use `distrobox create --nvidia` on this CachyOS + rootless-podman
  host — it hangs in a driver-remount loop (see
  [[distrobox-nvidia-use-cdi-not-nvidia-flag]]).
- **An unresolvable CDI device fails at box *start*, not at box *create*, and the
  symptom is a lying export error** (hit 2026-08-06 on an AMD-only host —
  Radeon `1002:1586`, no `nvidia-smi`, no `/etc/cdi`). `distrobox create` happily
  records `--device nvidia.com/gpu=all` and exits 0; `tools setup` then prints:
  ```
  ==> Exporting binary 'nvtop' to ~/.local/bin...
  Error: cannot find 'nvtop' inside container
  ==> Creating desktop entry for 'nvtop'...
  Error: cannot find 'nvtop' inside container
  ...
  Done. 'nvtop' is ready.
  ```
  and still says `Done.` That reads like a broken image (missing binary), but the
  image is fine — every `distrobox enter` fails to start the container, so
  `command -pv nvtop` returns nothing and both export types report "cannot find".
  **Diagnose with `podman ps -a` / `distrobox list` first** — a box stuck in
  `Created` (never `Up`) means it can't start. Then run `distrobox enter <box>`
  by hand to see the real error, here `setting up CDI devices: unresolvable CDI
  devices nvidia.com/gpu=all`. This applies to any app whose `create_flags`
  reference a device the host may not have, not just nvtop.
- **AMD/Intel-only hosts** are now the default path (see the wizard note above),
  so this no longer needs a manual workaround. Previously the fix was to delete
  `create_flags` by hand; if you hit an already-broken box, `tools setup nvtop`
  and choose **AMD / Intel** — no image rebuild is actually required, but setup
  rebuilds anyway since it's idempotent.
- **If NVIDIA GPUs don't show up** but nvtop otherwise runs, it's an NVML resolve
  problem: the CDI-injected `libnvidia-ml.so.1` must match the loaded host driver.
- **Verified end-to-end on hardware** (2026-07-23, CachyOS, 2×RTX 3090): image
  205 MB, nvtop 3.3.2, `libnvidia-ml.so.1` present via CDI, `/dev/nvidia0/1` +
  `/dev/dri/{card0,card1,renderD128,renderD129}` visible in the box, and a live
  frame enumerates "GeForce RTX 3090". Pattern mirrors amdgpu_top (default
  passthrough) + nvbandwidth (CDI).
- **`nvidia-cdi-hook (exit code: 1)` on box start (host-wide, every CDI box).**
  Two independent triggers, both fixed the same way — by regenerating
  `/etc/cdi/nvidia.yaml`: (1) toolkit 1.19.x emits a
  `disable-device-node-modification` hook that fails under distrobox (can't mount
  its `/proc/driver/nvidia/params`); suppress with
  `--disable-hook disable-device-node-modification`. (2) `nvidia.com/gpu=all`
  lists GPUs by UUID + fixed device minors, so if the *installed* GPUs differ from
  the set the spec was generated for (add/remove/move a card, PCIe-switch
  re-enumeration) resolving `all` fails. This host churned 2×3090 → 3090+3080 →
  2×3090+3080; when the cards happen to match the spec it "just works" untouched.
- **NO box recreation / rebuild / re-export is needed — podman 6.0.1 re-reads the
  CDI spec on every `start`.** Just regenerate the spec and the existing box
  starts (verified: a stale box that wouldn't start started instantly after a
  bare regenerate, no `distrobox rm`/`create`). Durable fix on this host = a
  boot-time systemd unit `nvidia-cdi-service.service` that runs
  `nvidia-ctk cdi generate --disable-hook disable-device-node-modification
  --output /etc/cdi/nvidia.yaml` (with `ExecStartPre=nvidia-smi -L`) so the spec
  always matches current hardware. See [[cdi-disable-device-node-modification-hook]]
  and [[distrobox-nvidia-use-cdi-not-nvidia-flag]]. Note: distrobox creates these
  boxes `--privileged` with `-v /dev:/dev:rslave`, so GPU nodes are present
  regardless of CDI — CDI only injects the driver libs.
- **Host `tools` not on PATH:** on this host `tools` is not symlinked in
  `~/.local/bin`, and there are two repo checkouts
  (`~/Developer/linux-tools` = canonical + `~/Developer/projects/linux-tools`).
  Drive setup with `distrobox-host-exec bash -lc './tools.sh setup nvtop'` from
  the working copy rather than the `tools` shim.
