## chrome

Google Chrome stable from Google's own APT repo, in an `ubuntu:24.04` box,
exported to the host menu with `app:google-chrome:Google Chrome`. One of the
oldest apps in the repo and one of the simplest — no wizard, no `create_flags`,
no wrapper scripts.

It is also **infrastructure for two other apps**: `apps/openclaw/openclaw-dashboard`
and `apps/comfyui/comfyui-open` both look for `chrome-box` in `distrobox list` and,
if present, open their web UI as an app-mode Chrome window
(`distrobox-host-exec distrobox enter chrome-box -- google-chrome --app=…`) with a
per-app profile under `~/.openclaw/` / `~/.comfyui/`. They fall back to `xdg-open`
when the box is absent. So changing the box name or breaking the image breaks
those two launchers too.

## Implementation

- `Dockerfile` — `FROM --platform=linux/amd64 docker.io/ubuntu:24.04` (Chrome is
  amd64-only), Google's signing key dearmored into
  `/usr/share/keyrings/google-chrome.gpg`, the stable APT repo, then
  `google-chrome-stable`. Beyond that: `curl`+`gnupg` (key fetch; `curl` also lets
  `distrobox-host-exec` bootstrap `host-spawn`), `libpulse0`+`libasound2t64`
  (audio), `git` (shared-`$HOME` dotfiles run in this box too) and the Noto font
  set (see pitfalls).
- `exports` — a single `app:` line. Chrome's `.deb` installs its own
  `/usr/share/applications/google-chrome.desktop`, so `distrobox-export --app`
  finds it; that is what keeps the MimeType list and the *New window* /
  *New incognito window* actions, which a hand-written `gui:` entry would lose.
- `icon.png` bundled, so the host entry gets the Chrome icon rather than whatever
  `resolve_icon` finds in the container.
- `category` = `Browsers`; `description` = `Google Chrome`.

## Pitfalls and notes

- **GPU acceleration needs nothing from this app.** Verified via
  `WEBGL_debug_renderer_info` in a headless run: `ANGLE (AMD, Radeon 8060S
  Graphics (radeonsi gfx1151 LLVM 20.1.2 DRM 3.64), OpenGL 4.6)`. Two reasons,
  both worth remembering repo-wide:
  1. `distrobox-init` apt-installs the GL/Vulkan userspace (`libgl1`, `libegl1`,
     `libegl-mesa0`, `libglx-mesa0`, `libvulkan1`, `mesa-vulkan-drivers`) into
     *every* Debian/Ubuntu box on first start — see the package list near the end
     of `/usr/local/bin/distrobox-init`. The Fedora-base guidance in `CLAUDE.md`
     (spell out `mesa-vulkan-drivers` etc.) does not apply to Ubuntu bases.
  2. `/dev/dri` is usable with **no `--group-add`**: distrobox shares `/dev` and
     keeps the host user's supplementary groups, so `card1`/`renderD128` appear as
     `nobody nogroup` but `crw-rw----+` (ACL) and are read/write for the container
     user. Don't "fix" this by adding numeric GIDs to `create_flags`.
- **Hardware video decode works, and takes exactly one flag:
  `--disable-gpu-driver-bug-workarounds`.** Without it Chrome logs
  `vaapi_wrapper.cc] GetHandle(): VAAPI has been disabled due to a detected driver
  bug` on this Mesa 25.2.8 / radeonsi gfx1151 combination and decodes on the CPU.
  Measured on a playing 1080p H.264 clip: **~35 % of one core software vs ~7 %
  hardware** (45 % when explicitly disabled again through a user flags file), with
  `vaapi_video_decoder.cc] VaapiVideoDecoder()` in the log on the hardware side.
  Nothing else was needed — not `VaapiIgnoreDriverChecks`, not
  `AcceleratedVideoDecodeLinux{GL,ZeroCopyGL}`, not `VaapiVideoDecoder`, not
  `UseMultiPlaneFormatForHardwareVideo`, not `LIBVA_DRIVER_NAME=radeonsi`, not
  `--use-angle=vulkan` + `Vulkan,VulkanFromANGLE,DefaultANGLEVulkan`, not
  `--ignore-gpu-blocklist`. Both CachyOS-wiki flag sets were tested in full and
  changed nothing on their own. **The flag disables ALL of Chrome's GPU driver bug
  workarounds**, not just the VA-API one — first suspect for any rendering glitch
  in this box.
- **How the flag gets in: a `dpkg-divert` wrapper, because there is no other
  hook.** Google's `.deb` launcher sets only `CHROME_VERSION_EXTRA` and
  `GNOME_DISABLE_CRASH_DIALOG` before `exec -a "$0" "$HERE/chrome" "$@"` — it does
  not source `/etc/default/google-chrome` and honours no `*_FLAGS` variable — and
  the `app:` export reuses Chrome's own `.desktop`
  (`Exec=/usr/bin/google-chrome-stable %U`). So the Dockerfile diverts that path to
  `.real` and installs `apps/chrome/google-chrome-wrapper` in its place; the
  diversion is what survives an `apt upgrade` of Chrome inside the box (a plain
  overwrite would not). The wrapper reads one flag per line from
  `~/.config/chrome-flags.conf` if present, else `/etc/chrome-flags.conf` (shipped
  with just the one flag) — deliberately the CachyOS file name so its wiki's lists
  paste in. User file wins outright rather than merging, which is what makes
  "turn the override off" possible without touching the image; verified by doing
  exactly that and watching decode fall back to software.
- **`libpci3` was a second, independent gap** (fixed in the same branch). Before
  it, the failure came one step earlier — `failed to find a suitable render node`
  — because Chrome dlopens libpci for the GPU's PCI IDs and without it
  `chrome://gpu` shows `GPU0: VENDOR = 0x0000, DEVICE = 0x0000`, leaving nothing to
  match a render node against. **Reusable diagnostic for any GUI box here:
  `VENDOR=0x0000` in `chrome://gpu` means libpci is missing, not that the GPU is
  unknown.**
- **Three signals that lie on this machine** — each cost real time:
  1. `chrome://gpu`'s *Video Decode: Hardware accelerated* is a blocklist status,
     not playback truth. It printed that throughout the software-decode period.
     This burned commit `911fe08`, which "corrected" the README to claim decode
     worked on the strength of that line.
  2. `vcn_busy_percent` — and so `amdgpu_top`'s Media row — reads `0` on gfx1151
     **even during confirmed hardware decode**, so the CachyOS wiki's
     amdgpu_top-media advice does not transfer. Reason: **on VCN 4.x the decoder
     rides the unified VCN queue, which the kernel accounts to `drm-engine-enc`**,
     not `drm-engine-dec`, and that sysfs counter does not track it. DRM `fdinfo`
     does: measured on 1080p, `drm-engine-enc` 23 % + `drm-engine-vpe` 28 % while
     decoding in hardware, both **entirely absent** in software, with
     `drm-engine-gfx` at 2 % either way. `chrome-decode-check` was rewritten around
     that and it is the signal to reach for in any future GPU-media question here.
  3. Grepping `/proc/<pid>/maps` for `*_drv_video.so` never matches on Ubuntu's
     Mesa 25 — the VA driver is a symlink to `libgallium-<ver>.so` and maps shows
     the resolved path (and libgallium is mapped for GL regardless).
  What is left that does not lie: total Chrome CPU during playback, the presence of
  the flag in `/proc/<pid>/cmdline`, and `chrome://media-internals`' `video_decoder`
  field.
- **`chrome-decode-check` traps found in review, all fixed — do not reintroduce:**
  (1) `awk`'s `print` renders sums past INT32_MAX through OFMT as `3.5e+09` on
  older mawk, and bash arithmetic cannot parse that — these counters are
  cumulative ns and pass that mark after ~2 s of engine time, so the sample would
  vanish and report software decode while counters climbed; use
  `printf "%.0f"`. (2) A process that exits mid-measurement must be *skipped*,
  not read as zero ticks, or its whole lifetime CPU is subtracted and the total
  goes negative — closing a tab during software playback would report "nothing was
  decoding". (3) The verdict keys on *any* video-engine time (>1 ms over the
  window), never a utilisation floor: low-resolution or low-frame-rate hardware
  decode can sit under 1 % of the engine, and in software the engines are absent
  from `fdinfo` entirely, so presence is the signal. (4) The flag check must be
  scoped to the browser process of the busiest instance (walk PPid up to the
  process whose parent is not Chrome). Checking "any Chrome process" borrows a
  flag from an unrelated window — observed live, reporting "software decode
  despite the flag" for an instance that had no flag — and grouping by
  `--user-data-dir` does not work because renderers do not carry it.
- **`chrome-decode-check` (host script, not exported) is the answer to "is it
  decoding on the GPU?"** It reports, in order of evidential weight: whether a
  `*_drv_video.so` is mapped into any Chrome process (decisive and
  codec-independent — the Mesa VA driver loads lazily on the first hardware
  decode), peak `vcn_busy_percent`, and the busiest Chrome process as a share of
  one core. Validated both ways during the review: paused browser → "nothing was
  decoding" (0 %), 1080p H.264 playing → "software decode" (34 %). It deliberately
  refuses to call an idle browser a pass, since that is the failure mode that
  produced several wrong readings here.
- **"The GPU is busy" is not evidence of hardware decode.** `gpu_busy_percent` sits
  at 10–33 % during any playback — frame upload, colour conversion, compositing,
  scaling all run on the graphics engine regardless of where decode happened. Only
  `vcn_busy_percent` tracks the decode block. This came up when the box's Chrome
  looked busy on a YouTube 4K tab; measuring it showed the tab was paused (no
  `pactl` sink-input, busiest renderer thread 5 % of one core) and no VA driver
  mapped in any Chrome process.
- **`amdgpu_top -d` describes what the VCN block can do** (here VCN 4.0: AVC, HEVC,
  VP9, AV1 decode up to 8192x4352), which is a useful sanity check that the
  hardware is not the limitation before blaming the container.
- **Two ways to measure nothing and believe it**, both hit during that review:
  1. `--headless=new` (and `--no-sandbox`) emit the VA-API render-node warning
     unconditionally, so headless proves nothing either way — test in a real window.
  2. A `<video>` that never started reads identically to flawless hardware decode
     (0 % engine, no CPU). Google's `gtv-videos-bucket/sample/*.mp4` URLs now return
     **403**, so several probe runs measured a blank page. Confirm playback first:
     the trick that worked was a local page whose script writes
     `currentTime`/`paused`/`videoWidth` into `document.title`, read from the host
     with `wmctrl -l`, plus `--autoplay-policy=no-user-gesture-required`.
     A reachable clip as of this writing:
     `https://test-videos.co.uk/vids/bigbuckbunny/mp4/h264/1080/Big_Buck_Bunny_1080_10s_5MB.mp4`.
  3. `pkill -f <pattern>` where the pattern also matches the shell running it kills
     that shell (exit 144) — use `pkill -f "[v]aprobe"`.
- **Why no flags are baked in:** Google's `.deb` wrapper
  (`/opt/google/chrome/google-chrome`) only sets `CHROME_VERSION_EXTRA` and
  `GNOME_DISABLE_CRASH_DIALOG` before `exec -a "$0" "$HERE/chrome" "$@"` — it does
  not source `/etc/default/google-chrome` any more and honours no `*_FLAGS`
  variable, and the `app:` export reuses Chrome's own `.desktop`
  (`Exec=/usr/bin/google-chrome-stable %U`). The only injection point left is
  replacing that `/usr/bin` symlink with a wrapper per the CLAUDE.md pattern, which
  `apt upgrade` inside the box would silently revert. Moot while no flag helps.
- **Don't read a Linux default as a container fault on `chrome://gpu`.** A healthy
  chrome-box shows `Vulkan`, `Skia Graphite`, `Direct Rendering Display
  Compositor`, `Raw Draw`, `TreesInViz` and `WebNN` as *Disabled* (Chrome renders
  via ANGLE/GL on Linux) with `Canvas`/`Compositing`/`Rasterization`/`WebGL`/
  `WebGPU` *Hardware accelerated*, and a *Problems Detected* list of generic Mesa
  workarounds (`disable_post_sub_buffers_for_onscreen_surfaces`,
  `disable(GL_KHR_blend_equation_advanced)`, `disable(GL_MESA_framebuffer_flip_y)`,
  `exit_on_context_lost`). None of that is container-specific.
- **Passwords work through the XDG Secret portal, not libsecret.** Chrome 148
  writes `os_crypt.portal.prev_init_success: true` into
  `~/.config/google-chrome/Local State`; the container has no `libsecret-1-0` or
  `gnome-keyring` and does not need them, because the host session bus is shared
  (`DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus`) and the host's
  `org.freedesktop.impl.portal.Secret` answers. If a host lacks a Secret portal
  backend, Chrome silently falls back to its obfuscated "basic" store — the
  failure is invisible in the UI, so check `Local State`.
- **Chrome's deps only bring `fonts-liberation`.** Before this review the box had
  108 fonts and *zero* emoji and *zero* CJK — every one of those 108 came from the
  host user's `~/.local/share/fonts` via shared `$HOME` (Nerd Fonts), because
  fontconfig in the container does **not** see the host's system fonts (they are
  under `/run/host`, which fontconfig never scans). Hence
  `fonts-noto-core`/`fonts-noto-color-emoji`/`fonts-noto-cjk` in the Dockerfile:
  without them emoji are tofu boxes and CJK pages have no fallback at all.
- **PWA ("Install as app") shortcuts land in the host menu broken.** Chrome writes
  `~/.local/share/applications/chrome-<app-id>-Default.desktop` (shared `$HOME`)
  with `Exec=/opt/google/chrome/google-chrome --app-id=…` — a container-only path,
  so from the host menu it silently does nothing. Icons land in the shared
  `~/.local/share/icons/hicolor/*/apps/` and are fine. Fix per entry:
  `distrobox enter chrome-box -- distrobox-export --app chrome-<app-id>-Default`,
  which rewrites `Exec=` through `distrobox-enter`. `cmd_export` will not do it —
  it only exports `google-chrome`, and its duplicate-cleanup loop matches on
  `Name=`, so unrelated PWA entries are correctly left alone. Observed in the wild
  with the ComfyUI PWA on this host (both the broken unprefixed entry and a
  hand-exported working `chrome-box-chrome-<id>-Default.desktop`).
- **`tools setup chrome` kills open Chrome windows**, including the app-mode
  openclaw/comfyui ones, because setup removes the box first. `tools export chrome`
  is the safe operation when only the `description`/label changed — it keeps the
  box and image and just rewrites the `.desktop` files (the terminal shortcut's
  `Name=` is built from `description`, which is why renaming the description
  requires a re-export to become visible).
- **Chrome self-updates through APT inside the box**, not via the host. A rebuild
  (`tools setup chrome`) pulls whatever is current stable; the profile in
  `~/.config/google-chrome/` is untouched by rebuilds since it lives in the shared
  host home. Never point a host-installed Chrome at that same profile.
- **The reviewed Dockerfile was verified by a side-tag build, not a reinstall.**
  `podman build -t localhost/linux-tools/chrome:reviewtest -f apps/chrome/Dockerfile
  apps/chrome` succeeded and the resulting image has `git 2.43.0`,
  `NotoColorEmoji.ttf` + `NotoSansCJK-*.ttc`, and Chrome 154.0.8037.57 — done that
  way deliberately, because `tools setup chrome` would have killed the Chrome
  windows that were open at the time. The `latest` image and the live box only pick
  the changes up on the next `tools setup chrome`. The fonts cost ~140 MB
  (`fonts-noto-cjk` 89 MB, `fonts-noto-core` 42 MB, emoji 10 MB); the rebuilt image
  still came out smaller than the 4-month-old one (1.13 GB vs 1.63 GB).
- Was on both `LEGACY_NO_README` and `LEGACY_UNQUALIFIED_FROM` in
  `scripts/lint-apps.sh`; this review added the README and qualified the `FROM`, so
  both entries were removed and the app is now held to the current contract.
