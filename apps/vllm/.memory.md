## vllm

OpenAI-compatible LLM inference server with AMD ROCm GPU acceleration. Serves models via HTTP API on port 8000, compatible with any OpenAI client SDK. Packaged using the official `vllm/vllm-openai-rocm` Docker image.

## Implementation

**Base image**: `docker.io/vllm/vllm-openai-rocm:${VLLM_TAG}` (`ARG VLLM_TAG=latest` before the `FROM`)
- Official vLLM image with ROCm + PyTorch pre-installed; no separate vLLM installation needed.
- The default keeps a non-interactive `tools setup vllm` on `:latest`, as it was before the wizard existed.

**Release picker**: `wizard/00-release.buildarg` — `arg|VLLM_TAG`, an `items-cmd` that reads the
published tags from the Docker Hub API, and `notes-repo|vllm-project/vllm` for the notes.
- The versions deliberately come from **Docker Hub, not GitHub releases**: the value goes straight
  into the `FROM` line, so a version with no published ROCm image would be a pull failure at build
  time. Docker Hub is also the only source that knows about `nightly`, which GitHub never tags.
- The two lists agree today (checked: the 15 newest GitHub release tags all have matching image
  tags), so a plain `releases|vllm-project/vllm` page would look identical — right up until it
  didn't.
- `?name=v` on the tags query filters server-side, which is what keeps the query durable: the repo
  publishes a `nightly-<sha>` tag per commit, and those would otherwise push the version tags off
  the first page as they accumulate (92 tags total today, 52 with the filter).
- Item order is `latest`, then the 10 newest `vX.Y.Z` tags, then `nightly` — first line is the
  default, and `nightly` sits last because it is the riskiest choice, not the newest one.
- No tag template on `notes-repo`: image tags and release tags are both `vX.Y.Z` verbatim. `latest`
  gets the newest non-prerelease release's notes for free (`newestStable` in `tui/releases.go`);
  `nightly` matches nothing and shows no notes, which is correct.
- The tag regex is `^v[0-9]+(\.[0-9]+){1,3}$`, so 4-component tags like `v0.10.1.1` survive while
  `v0.10.1rc1` and `v0.8.5.post1` are filtered out — rc images should not be in a version picker,
  and a `.post` release is covered by `latest`.

**Python/vllm path**: `vllm` binary lives at `/usr/local/bin/vllm` in the image. A `/usr/bin/vllm` shim bridges it for `command -pv` (which doesn't search `/usr/local/bin`).

**Server wrapper**: `/usr/bin/vllm-serve` launches `python -m vllm.entrypoints.openai.api_server` with Strix Halo env vars baked in. Accepts all vLLM server flags as arguments (e.g. `--model`, `--max-model-len`, `--dtype`).

**Model storage**: `~/.cache/huggingface` — HuggingFace default, automatically persisted via Distrobox shared `$HOME`. No extra volume mount needed.

**HF_TOKEN**: Not baked into the image. Inherited from the host shell environment at runtime (`export HF_TOKEN=...` in `~/.zshrc`/`~/.bashrc`). Recommended: store via Linux keyring (`secret-tool`) and retrieve in rc files.

**Port**: 8000. Distrobox uses `--network host` so no port mapping needed — `http://localhost:8000` is directly accessible on the host.

**Exports**: `bin:vllm` (full CLI) + `bin:vllm-serve` (convenience server wrapper).

**Docs**: `README.md` (added alongside the wizard) covers install, both commands, the OpenAI API usage, cache paths, `HF_TOKEN`, and the GPU/VRAM notes.

**create_flags**: `--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 --cap-add SYS_PTRACE --security-opt seccomp=unconfined --ipc=host`
- `/dev/kfd` — AMD ROCm compute device.
- GIDs 44=video, 992=render (numeric because Ubuntu-based images lack these group names in `/etc/group`).
- `--cap-add SYS_PTRACE` — required by vLLM ROCm internals.
- `--ipc=host` — required for ROCm shared-memory IPC.

## Usage

```bash
# Pick a version at install time (interactive only; non-interactive takes latest)
tools setup vllm

# Start server with a model
vllm-serve --model Qwen/Qwen3-0.6B

# Full vLLM CLI (model is positional here)
vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192

# Query the API
curl http://localhost:8000/v1/models
curl http://localhost:8000/v1/completions -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-0.6B", "prompt": "Hello", "max_tokens": 100}'
```

## Pitfalls and notes

- **`/usr/local/bin/vllm` path**: `command -pv` (used by `tools.sh` for `bin:` exports) does not search `/usr/local/bin`. The `/usr/bin/vllm` shim is required.
- **No venv in this image** (verified in the built box): `python` is `/usr/bin/python` and imports vLLM directly, unlike the `rocm/pytorch` images used by comfyui/unsloth where everything lives in `/opt/venv`. The `vllm-serve` wrapper's bare `python -m vllm...` is therefore correct and needs no venv path.
- **Strix Halo env vars**: Same set as comfyui — `HSA_ENABLE_SDMA=0`, `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`, `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`, `TORCH_BLAS_PREFER_HIPBLASLT=1`. May be fixable/removable in future ROCm releases.
- **MIOpen first-run slowness**: First model load triggers GPU kernel compilation. Cache persists at `~/.cache/miopen`.
- **Image size**: `vllm-openai-rocm` images are large (15–25 GB). Allow significant pull/build time.
- **`nightly` tag**: Use `:nightly` for cutting-edge features/fixes; may be less stable than `:latest`. It is offered by the wizard, listed last.
- **`vllm serve` takes the model positionally** (`vllm serve Qwen/Qwen3-0.6B`), while the `vllm-serve` wrapper goes through `python -m vllm.entrypoints.openai.api_server`, which wants `--model`. Both are documented in `README.md`; don't "fix" one to look like the other.
