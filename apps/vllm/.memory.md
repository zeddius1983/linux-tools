## vllm

OpenAI-compatible LLM inference server on an AMD (ROCm) or NVIDIA (CUDA) GPU. Serves models via HTTP API on port 8000, compatible with any OpenAI client SDK. Packaged using the official upstream images — `vllm/vllm-openai-rocm` and `vllm/vllm-openai`.

## Implementation

**Base images**: `docker.io/vllm/vllm-openai-rocm:${VLLM_TAG}` (AMD) and `docker.io/vllm/vllm-openai:${VLLM_TAG}` (NVIDIA), as two stages the final `FROM base-${VLLM_GPU}` picks between — the comfyui pattern. Buildah prunes the unreferenced stage, so choosing one backend never pulls the other's ~20 GB image (verified: an `nvidia` build succeeds with a deliberately bogus `ROCM_BASE`).

**Why not one image for both**: vLLM compiles its kernels per accelerator and the PyTorch under them is `torch+rocm` *or* `torch+cu12`, never both. Unlike llama.cpp there is no runtime backend dispatch (`GGML_BACKEND_DL`), so a combined image would be ~40 GB and still pick one stack at launch. Upstream publishes two images for exactly this reason.

**GPU page**: `wizard/00-gpu.runtime` — `arg|VLLM_GPU`, items `AMD (ROCm)|amd` and `NVIDIA (CUDA)|nvidia`. The value selects both the build stage and `create_flags.<value>`, so the question is asked once. Applicable to `setup,build,create`.

**Release picker**: `wizard/01-release.buildarg` — `arg|VLLM_TAG`, `releases|vllm-project/vllm`, plus `extra|latest` and `extra|nightly` (both tags verified present in *both* repos).
- The version list comes from **GitHub releases, not Docker Hub tags**, and that is a deliberate reversal of how this page started. The first version of it read the ROCm repo's tags (`?name=v`, filtered and sorted), which had the nice property that every offered value was an image known to exist. That does not survive the second backend: a `.buildarg` items-cmd is a fixed shell command and cannot see the GPU page's answer, so one list has to serve both repos — and the CUDA repo cannot be enumerated in one request. It carries ~600 tags against ROCm's ~90, with per-arch and per-CUDA-version variants (`v0.29.0-cu129`, `-aarch64-`, `-ubuntu2404`) plus a `nightly-dev-<arch>-<sha>` per commit; `?name=v&page_size=100` surfaces only 6 clean versions, and `ordering=-name` returns the *oldest* ones. Release tags, by contrast, exist verbatim in both repos.
- What that costs: a release whose image build failed for one backend would still be offered. That is a fast manifest-fetch failure at build time, not a wasted 20 GB pull.
- Default is now the newest release tag rather than `latest` — the same image at install time, but pinned. `latest` and `nightly` are listed after the releases, as `extra|` values always are.
- `releases|` also means notes for every item in one API call, so no `notes-repo|` line is needed.

**Server wrapper**: `/usr/bin/vllm-serve` launches `python -m vllm.entrypoints.openai.api_server` on `0.0.0.0:8000`, and accepts all vLLM server flags (e.g. `--model`, `--max-model-len`, `--dtype`).
- It sources `/etc/vllm-env`, which each base stage writes for itself: the ROCm/Strix Halo exports on AMD, a comment on NVIDIA. Keeping them out of the wrapper is what lets one wrapper serve both variants.
- `/etc/vllm-gpu` records the variant (`amd`/`nvidia`) — the quickest way to tell what a box was built as. Mirrors comfyui's `/etc/comfyui-gpu`.
- Both the CLI path and the Python path are resolved at **build time** (`command -v vllm`, `command -v python || command -v python3`) and baked into the wrappers, rather than hard-coded: the two upstream images are separate builds and need not agree on layout. The `/usr/bin/vllm` shim is skipped entirely if a future image already ships the CLI there, which would otherwise make it call itself.

**Model storage**: `~/.cache/huggingface` — HuggingFace default, automatically persisted via Distrobox shared `$HOME`. No extra volume mount needed.

**HF_TOKEN**: Not baked into the image. Inherited from the host shell environment at runtime (`export HF_TOKEN=...` in `~/.zshrc`/`~/.bashrc`). Recommended: store via Linux keyring (`secret-tool`) and retrieve in rc files.

**Port**: 8000. Distrobox uses `--network host` so no port mapping needed — `http://localhost:8000` is directly accessible on the host.

**Exports**: `bin:vllm` (full CLI) + `bin:vllm-serve` (convenience server wrapper).

**Docs**: `README.md` (added alongside the wizard) covers install, both commands, the OpenAI API usage, cache paths, `HF_TOKEN`, and the GPU/VRAM notes.

**create_flags**: `--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 --cap-add SYS_PTRACE --security-opt seccomp=unconfined --ipc=host`, with `create_flags.nvidia` swapping `/dev/kfd` for `--device nvidia.com/gpu=all` (CDI).
- `/dev/kfd` — AMD ROCm compute device.
- GIDs 44=video, 992=render (numeric because Ubuntu-based images lack these group names in `/etc/group`).
- `--cap-add SYS_PTRACE` — required by vLLM ROCm internals.
- `--ipc=host` — required for ROCm shared-memory IPC.
- NVIDIA goes through CDI, **not** `distrobox create --nvidia`: on a rootless-podman host that bind-mounts the whole host driver on every start and can wedge in a remount loop (post-mortem in `apps/lmstudio/README.md`). Needs `/etc/cdi/nvidia.yaml` on the host — see the `nvidia-cdi-service` app.

## Usage

```bash
# Pick a backend and a version at install time (interactive only;
# non-interactive builds the amd variant on :latest)
tools setup vllm

# Start server with a model
vllm-serve --model Qwen/Qwen3-0.6B

# Full vLLM CLI (model is positional here)
vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192

# Query the API
curl http://localhost:8000/v1/models
curl http://localhost:8000/v1/completions -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-0.6B", "prompt": "Hello", "max_tokens": 100}'
```

## Pitfalls and notes

- **`/usr/local/bin/vllm` path**: both images put the CLI there, and `command -pv` (used by `tools.sh` for `bin:` exports) does not search `/usr/local/bin`. The `/usr/bin/vllm` shim is required.
- **No venv in the ROCm image** (verified in the built box): `python` is `/usr/bin/python` and imports vLLM directly, unlike the `rocm/pytorch` images used by comfyui/unsloth where everything lives in `/opt/venv`. The `vllm-serve` wrapper's bare `python -m vllm...` is therefore correct and needs no venv path.
- **Strix Halo env vars**: Same set as comfyui — `HSA_ENABLE_SDMA=0`, `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`, `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`, `TORCH_BLAS_PREFER_HIPBLASLT=1`. AMD stage only, in `/etc/vllm-env`. May be fixable/removable in future ROCm releases.
- **One backend per install**: `<app>-box` and `linux-tools/<app>` are derived from the app name, so this app is one box and one image — an AMD and an NVIDIA vLLM cannot coexist. Switching backends is a full `tools setup vllm` rebuild. Running both at once would need a second app (see ROADMAP: cloned apps).
- **MIOpen first-run slowness**: First model load triggers GPU kernel compilation. Cache persists at `~/.cache/miopen`.
- **Image size**: `vllm-openai-rocm` images are large (15–25 GB). Allow significant pull/build time.
- **`nightly` tag**: Use `:nightly` for cutting-edge features/fixes; may be less stable than `:latest`. It is offered by the wizard, listed last.
- **`vllm serve` takes the model positionally** (`vllm serve Qwen/Qwen3-0.6B`), while the `vllm-serve` wrapper goes through `python -m vllm.entrypoints.openai.api_server`, which wants `--model`. Both are documented in `README.md`; don't "fix" one to look like the other.
