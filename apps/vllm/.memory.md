## vllm

OpenAI-compatible LLM inference server on an AMD (ROCm) or NVIDIA (CUDA) GPU. Serves models via HTTP API on port 8000, compatible with any OpenAI client SDK. Packaged using the official upstream images — `vllm/vllm-openai-rocm` and `vllm/vllm-openai`.

## Implementation

**Base images**: `docker.io/vllm/vllm-openai-rocm:${VLLM_TAG}` (AMD) and `docker.io/vllm/vllm-openai:${VLLM_TAG}` (NVIDIA), as two stages the final `FROM base-${VLLM_GPU}` picks between — the comfyui pattern. Buildah prunes the unreferenced stage, so choosing one backend never pulls the other's ~20 GB image (verified: an `nvidia` build succeeds with a deliberately bogus `ROCM_BASE`).

**Why not one image for both**: vLLM compiles its kernels per accelerator and the PyTorch under them is `torch+rocm` *or* `torch+cu12`, never both. Unlike llama.cpp there is no runtime backend dispatch (`GGML_BACKEND_DL`), so a combined image would be ~40 GB and still pick one stack at launch. Upstream publishes two images for exactly this reason.

**GPU page**: `wizard/00-gpu.runtime` — `arg|VLLM_GPU`, items `AMD (ROCm)|amd` and `NVIDIA (CUDA)|nvidia`. The value selects both the build stage and `create_flags.<value>`, so the question is asked once. Applicable to `setup,build,create`.

**Release picker**: `wizard/01-release.buildarg` — `arg|VLLM_TAG`, `releases|vllm-project/vllm`, plus `extra|latest` and `extra|nightly` (both tags verified present in *both* repos).
- The version list comes from **GitHub releases, not Docker Hub tags**, and that is a deliberate reversal of how this page started. The first version of it read the ROCm repo's tags (`?name=v`, filtered and sorted), which had the nice property that every offered value was an image known to exist. That does not survive the second backend: a `.buildarg` items-cmd is a fixed shell command and cannot see the GPU page's answer, so one list has to serve both repos — and the CUDA repo cannot be enumerated in one request. It carries ~600 tags against ROCm's ~90, with per-arch and per-CUDA-version variants (`v0.29.0-cu129`, `-aarch64-`, `-ubuntu2404`) plus a `nightly-dev-<arch>-<sha>` per commit; `?name=v&page_size=100` surfaces only 6 clean versions, and `ordering=-name` returns the *oldest* ones. Release tags, by contrast, exist verbatim in both repos.
- What that costs: a release whose image build failed for one backend would still be offered. That is a fast manifest-fetch failure at build time, not a wasted 20 GB pull.
- Default is now the newest release tag rather than `latest` — the same image at install time, but pinned. `latest` and `nightly` are listed after the releases, as `extra|` values always are.
- `releases|` also means notes for every item in one API call, so no `notes-repo|` line is needed.

**Server wrapper**: `/usr/bin/vllm-serve` runs `vllm serve --host 0.0.0.0 --port 8000 "$@"`, and accepts all vLLM server flags (e.g. `--model`, `--max-model-len`, `--dtype`) plus the positional model tag.
- It sources `/etc/vllm-env`, which each base stage writes for itself: the ROCm/Strix Halo exports on AMD, a comment on NVIDIA. Keeping them out of the wrapper is what lets one wrapper serve both variants.
- `/etc/vllm-gpu` records the variant (`amd`/`nvidia`) — the quickest way to tell what a box was built as. Mirrors comfyui's `/etc/comfyui-gpu`.
- The CLI path is resolved at **build time** (`command -v vllm`) and baked into both wrappers, rather than hard-coded: the two upstream images are separate builds and need not agree on layout. The `/usr/bin/vllm` shim is skipped entirely if a future image already ships the CLI there, which would otherwise make it call itself.

**Model storage**: `~/.cache/huggingface` — HuggingFace default, automatically persisted via Distrobox shared `$HOME`. No extra volume mount needed.

**HF_TOKEN**: Not baked into the image. Inherited from the host shell environment at runtime (`export HF_TOKEN=...` in `~/.zshrc`/`~/.bashrc`). Recommended: store via Linux keyring (`secret-tool`) and retrieve in rc files.

**Port**: 8000. Distrobox uses `--network host` so no port mapping needed — `http://localhost:8000` is directly accessible on the host.

**Exports**: `bin:vllm` (full CLI) + `bin:vllm-serve` (convenience server wrapper).

**Docs**: `README.md` (added alongside the wizard) covers install, both commands, the OpenAI API usage, cache paths, `HF_TOKEN`, and the GPU/VRAM notes.

**create_flags**: `--device /dev/kfd --device /dev/dri --group-add 44 --group-add 992 --cap-add SYS_PTRACE --security-opt seccomp=unconfined --ipc=host`, with `create_flags.nvidia` swapping `/dev/kfd` for `--device nvidia.com/gpu=all` (CDI).
- `/dev/kfd` — AMD ROCm compute device.
- GIDs 44=video, 992=render (numeric because Ubuntu-based images lack these group names in `/etc/group`).
- `--cap-add SYS_PTRACE` — required by vLLM ROCm internals.
- `--ipc=host` — required for ROCm shared-memory IPC.
- NVIDIA goes through CDI, **not** `distrobox create --nvidia`: on a rootless-podman host that bind-mounts the whole host driver on every start and can wedge in a remount loop (post-mortem in `apps/lmstudio/README.md`). Needs `/etc/cdi/nvidia.yaml` on the host — see the `nvidia-cdi-service` app.

## Usage

```bash
# Pick a backend and a version at install time (interactive only;
# non-interactive builds the amd variant on :latest)
tools setup vllm

# Start server with a model
vllm-serve --model Qwen/Qwen3-0.6B

# Full vLLM CLI (model is positional here)
vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192

# Query the API
curl http://localhost:8000/v1/models
curl http://localhost:8000/v1/completions -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-0.6B", "prompt": "Hello", "max_tokens": 100}'
```

### Serving larger models on gfx1151 (investigated 2026-09-13, vLLM 0.29.0+rocm723)

- **Quantization support was established by load tests, not by reading the platform list.** `RocmPlatform.supported_quantization` lists nearly everything (`awq`, `gptq`, `compressed-tensors`, `fp8*`, `mxfp4`, `mxfp8`, `modelopt_fp4`, `quark`, …), which says what the platform will *accept*, not what runs. The ROCm wheel has none of the CUDA quant kernels in `torch.ops._C` (`awq_gemm`, `gptq_gemm`, `*_marlin_gemm`, `machete_mm`, `scaled_fp4_quant` are all absent). Results:
  - **AWQ ✅** — `Qwen/Qwen2.5-0.5B-Instruct-AWQ` greedy output matched the bf16 model ("The capital of France is Paris…", "2 + 2 = 4"). Runs through `awq_triton`. A first sample at the default `temperature=1.0` came out as mixed Chinese/Arabic, which looked like broken dequant and was not — always compare greedy against a baseline before concluding a kernel is wrong.
  - **compressed-tensors w4a16 ✅** — `nm-testing/SmolLM-1.7B-Instruct-quantized.w4a16` coherent; real models log `Using RDNAHybridW4A16LinearKernel`, a kernel written for this architecture.
  - **FP8 ❌** — `quantization="fp8"` on a bf16 model: `Engine core initialization failed`.
  - **MXFP4/MXFP8 ❌** — `mxfp4.py` gates its AMD path on `on_gfx1250()`.
  - **NVFP4 ❌** — not load-tested; its kernel is absent and it is Blackwell-targeted.
  - A repo id I first used for the w4a16 probe (`RedHatAI/Qwen2.5-0.5B-Instruct-quantized.w4a16`) does not exist; my HF API existence check printed "OK" for it because the error response was still valid JSON. Check `HTTP` status, not parseability.
- **Quantized Qwen3.8-27B builds are NVFP4/FP8 only** (`nvidia/…-NVFP4`, `unsloth/…-NVFP4`, `Qwen/Qwen3.8-27B-FP8`, …) — the family went Blackwell-first. gemma-4 QAT w4a16 and cyankiwi's AWQ builds are what run here.
- **Hybrid GDN models + GPU graphs fail at the default `max_num_seqs`.** Qwen3.5/3.6 keep one fixed-size recurrent-state ("Mamba cache") block per running sequence. `--enforce-eager` never checks this, so a model that starts fine in eager can fail once graphs are on: `ValueError: max_num_seqs (256) exceeds available Mamba cache blocks (191)` — and only *after* ~2 minutes of graph capture. What shrank the pool between the working eager run and the failing one: utilization 0.35 → 0.30 and 2.53 GiB of graph memory, taking KV memory from 17.57 to 9.16 GiB. `--max-num-seqs 32` fixes it.
- **Graph capture size comes from `max_num_seqs`.** `config/vllm.py`: `max_cudagraph_capture_size = min(max_num_seqs * decode_query_len * 2, 512)`, sizes `[1, 2, 4] + range(8, 256, 8) + range(256, max + 1, 16)`. At 256 that is 51 shapes (2m09s, 2.53 GiB); at 32 it is 11 (14s + 17s, 0.58 GiB). Graph recordings hold pointers into the live process's GPU memory, so unlike `torch.compile` output they are redone on every start.
- **The compile cache is keyed on flags, and `--max-num-seqs` is part of the key.** Same model: a run with default `max_num_seqs` hit `torch_aot_compile/e3996ace…` in 0.62 s; adding `--max-num-seqs 32` missed, wrote `…/a71ce7e7b0`, and took 133.94 s. Pick a flag set and keep it.
- **Startup phases, Qwen3.6-27B AWQ, measured:** read weights 4.4 s, weight repack for the RDNA kernel ~24 s, compile 134 s (cache miss) or 0.6 s (hit), profiling/warmup run 64–93 s, graph capture 14–17 s — twice, because the memory profiler captures once to estimate (`VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` drops that) — plus 13 s multimodal warmup (`--language-model-only` drops it). Warm-cache, trimmed startup is estimated at ~2 minutes from those phases; it was not measured end to end.
- **Throughput: eager only.** Qwen3.6-27B AWQ with `--enforce-eager` measured **4.5 tok/s** (200 tokens in 44.6 s). The compiled-mode probe was killed by a session exit before it ran, so there is **no compiled number yet** — measure it before writing performance claims anywhere.
- **Decode-path fallbacks on this model**, from the startup log: `Cannot use ROCm custom paged attention kernel, falling back to Triton implementation`; `Falling back to the Triton GDN decode path` (the fused GDN kernel is CUDA 8.0+ only); decoder attention `ROCM_ATTN` after `TURBOQUANT` is rejected.
- **`FLASH_ATTENTION_TRITON_AMD_ENABLE=TRUE`** — `flash_attn_triton_available()` in `platforms/rocm.py` logs the hint only when on gfx1x *and* the Triton-AMD kernels are installed (both `flash_attn.flash_attn_triton_amd` and `aiter…flash_attn_triton_amd` are present in this image). Setting it switched only the ViT/multimodal encoder to Flash Attention; the text decoder stayed on `ROCM_ATTN` → Triton paged attention. Worth something for image inputs, nothing for chat throughput.
- **Host environment variables do reach the server** through the exported wrappers: `FOO=1 distrobox enter vllm-box -- printenv FOO` prints `1`, and a host-set `FLASH_ATTENTION_TRITON_AMD_ENABLE` took effect in a real run. So `VAR=x vllm-serve …` from the host works; no `env` inside the box is needed.
- **vLLM's own hint names the wrong flag**: the startup log suggests `--kv-cache-memory=<bytes>`, but the 0.29.0 CLI flag is `--kv-cache-memory-bytes`.
- **`--gpu-memory-utilization` is a fraction of total unified memory** (124 GiB here), not of free memory, and vLLM ignores other processes. A user-proposed 0.80 would have claimed ~99 GiB with 67 GiB actually free.

### Hugging Face downloads (hf_hub 1.30.0 in the image)

- **Xet was ~9× slower than the classic downloader on this network**, measured concurrently on the same link: gemma-4-31B via Xet at 1.12 MB/s vs Qwen3.6-27B with `HF_HUB_DISABLE_XET=1` at 10.07 MB/s.
- **Xet can wedge completely.** Signature: `/proc/<pid>/io` `rchar`/`wchar` byte-identical over 30 s and the `.incomplete` mtime frozen, while `~/.cache/huggingface/xet/logs/xet_*.log` keeps logging `Concurrency control for download: Decreased concurrency from 1 to 1; reason: success ratio below threshold (connection struggling)` about twice a second, and one thread sits at 100% CPU. The download wrote 20.44 GB and stopped with 2.9 GB left. Stopping a competing download did not unstick it, so contention was not the cause.
- **Partials never resume across runs, Xet or not.** Partial files are named `<sha>.<random>.incomplete`; a new attempt opens a new name and the next run deletes stale ones. First misread as a Xet-only behaviour — a `HF_HUB_DISABLE_XET=1` run showed the same naming and removed 11 GB of old partials on start.
- **Measuring download speed from the partial's size misleads**: writes land in bursts, so a 20-second window can read 0.0 MB/s mid-download. Use `/proc/<pid>/io` over 30 s or longer.
- **Don't let `vllm-serve` download a model.** EngineCore holds the partial and its lock, and `Loading model from scratch...` prints before any weights arrive — a wedged download reads as a hung server. Download with `hf download` first. Adding `ENV HF_HUB_DISABLE_XET=1` to the Dockerfile was considered but not done: the evidence is one network on one night.
- `ls -t` on this host is aliased to eza, which rejects `-t`; use `find -printf '%T@ %p'` to sort by mtime in scripts.

## Pitfalls and notes

- **`/usr/local/bin/vllm` path**: both images put the CLI there, and `command -pv` (used by `tools.sh` for `bin:` exports) does not search `/usr/local/bin`. The `/usr/bin/vllm` shim is required.
- **No venv in the ROCm image** (verified in the built box): `python` is `/usr/bin/python` and imports vLLM directly, unlike the `rocm/pytorch` images used by comfyui/unsloth where everything lives in `/opt/venv`. The `vllm-serve` wrapper's bare `python -m vllm...` is therefore correct and needs no venv path.
- **Strix Halo env vars**: Same set as comfyui — `HSA_ENABLE_SDMA=0`, `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`, `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`, `TORCH_BLAS_PREFER_HIPBLASLT=1`. AMD stage only, in `/etc/vllm-env`. May be fixable/removable in future ROCm releases.
- **One backend per install**: `<app>-box` and `linux-tools/<app>` are derived from the app name, so this app is one box and one image — an AMD and an NVIDIA vLLM cannot coexist. Switching backends is a full `tools setup vllm` rebuild. Running both at once would need a second app (see ROADMAP: cloned apps).
- **First start compiles, and it reads exactly like a hang.** Measured on this host (gfx1151, v0.29.0, `Qwen/Qwen3-0.6B`, `--max-model-len 8192`): **~9 minutes** from launch to the port opening, almost all of it `torch.compile` on a single core. Nothing listens on 8000 until compile → HIP graph capture (51 shapes) → KV-cache profiling all finish, so `curl` refuses the whole time and the log sits still after `Start compiling function`.
  - Ways to tell it is working, not stuck: `ps -o etime,times,%cpu -p $(pgrep -f VLLM::EngineCore)` showing ~100% (one core pegged = inductor); the log markers `torch.compile takes X s in total`, `Capturing CUDA graph shapes: n/51`, `init engine ... took X s`, `Starting vLLM API server`, `Application startup complete`; `VLLM_LOGGING_LEVEL=DEBUG` for per-sub-graph lines.
  - **Artifact counts are a trap**: inductor writes to `~/.cache/vllm/torch_compile_cache` only when a graph *completes*, so zero new files is normal during the first one. Its scratch dir is the **container's** `/tmp/torchinductor_$USER`, which Distrobox does not share with the host — check it from inside the box, not outside.
  - `--enforce-eager` skips compile and capture entirely (up in well under a minute, slower per token) — the right smoke test for "does this GPU work at all".
  - The compiled result caches under `~/.cache/vllm` on the host, so a second start of the same model with the same flags is quick. The cache is keyed on the config: changing `--max-model-len`, dtype or model recompiles.
- **MIOpen first-run slowness**: First model load triggers GPU kernel compilation. Cache persists at `~/.cache/miopen`.
- **Image size**: `vllm-openai-rocm` images are large — the v0.29.0 pull measured 38.8 GB and took ~20 minutes on a fast link. Allow for it.
- **`nightly` tag**: Use `:nightly` for cutting-edge features/fixes; may be less stable than `:latest`. It is offered by the wizard, listed last.
- **`python -m vllm.entrypoints.openai.api_server` is deprecated as of 0.29.0** — it warns twice on every start ("deprecated and will likely be unsupported", "may be removed in a future release") — so the wrapper runs `vllm serve` instead. Two traps in upstream's own deprecation text: it says to use **`vllm server`**, which is not a subcommand (`vllm --help` lists `chat, complete, serve, launch, bench, collect-env, run-batch`), and the module still works, so nothing fails loudly when a wrapper keeps using it. `vllm serve` accepts both the positional model tag and `--model`, so the wrapper's callers did not have to change.
- **The upstream images set an `ENTRYPOINT` of `vllm serve`**, which this Dockerfile does not reset. Harmless under Distrobox (it supplies its own entrypoint, and the box works), but a plain `podman run <image> bash -c ...` feeds the command to `vllm serve` as arguments and fails with a pydantic JSON error from `--compilation-config`. Use `--entrypoint bash` when testing the image directly.
