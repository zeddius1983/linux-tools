## openclaw

[OpenClaw](https://openclaw.ai/) — an open-source personal AI agent. It is a
long-running **Gateway** daemon (WebSocket + HTTP control plane, web Control UI,
OpenAI-compatible endpoints, channel connections to WhatsApp/Telegram/Discord)
plus an `openclaw` CLI that drives it.

Packaged as a container because it is a Node app with a large dependency tree
that wants a specific Node version, but it is unusual for this repo in that it is
a *service*, not a one-shot CLI. The interesting design work was all about how
the gateway stays running when the box has no init system.

## Implementation

Base `docker.io/ubuntu:24.04` + NodeSource Node 24. OpenClaw's engines expression
is `>=24.16.0 <25 || >=26.1.0`, enforced by a startup guard on *every* command, so
Ubuntu's own nodejs is not usable. Installed with `npm install -g openclaw@$OPENCLAW_VERSION`;
`wizard/00-release.buildarg` picks the version from the GitHub tags, same shape as
codex-cli's page.

Wrappers in `/usr/bin` (never `/usr/local/bin` — `command -pv` cannot see it):

- `openclaw-bin` — the real CLI, `exec /usr/bin/node "$(cat /usr/lib/openclaw/entrypoint)"`.
  The Dockerfile records where npm's shim pointed and then deletes the shim. See
  pitfall 1: the `#!/usr/bin/env node` shebang is actively dangerous here.
- `openclaw` — the exported CLI. Runs `ensure_systemd_bridge`, then injects a
  "don't install a daemon" flag into `onboard`/`setup` (pitfall 3).
- `openclaw-gateway` — foreground gateway, pinned to `--bind loopback` (pitfall 4).
- `openclaw-service` — `install|uninstall|status` for a **host** systemd user unit.
- `openclaw-dashboard` — resolves `dashboard --json` → `browserUrl`, opens it on the host.
- `openclaw-chat` — `openclaw tui`.
- `bridge.sh` — sourced by all of them; holds `ensure_systemd_bridge` and `OPENCLAW_BIN`.

### The systemd story (the load-bearing part)

Distrobox already shares the host's user runtime dir into every box:
`DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$UID/bus` is set, and
`/run/user/$UID/{bus,systemd}` are the host's. **`systemctl --user` therefore
already works from inside any box and drives the host's user manager** — verified
with `systemctl --user list-units` in `claude-code-box`, which lists host units.
No `distrobox-host-exec`, and so no dependency on the host having `flatpak`
installed (the repo-wide landmine in CLAUDE.md).

That is what `openclaw-service install` uses. It writes
`~/.config/systemd/user/openclaw-gateway.service` (shared `$HOME`, so it *is* the
file the host manager reads) and enables it. Because the unit runs on the host,
every path in it must be a host path — hence
`ExecStart=<host distrobox> enter -T -nw -n openclaw-box -- /usr/bin/openclaw-gateway`,
with the distrobox path probed from `/run/host/usr/local/bin` then
`/run/host/usr/bin` (it is at `/usr/local/bin/distrobox` on this host — a
curl-installed distrobox, not a distro package).

`ensure_systemd_bridge` adds the one missing piece, from
<https://wiki.archlinux.org/title/Distrobox>: `/run/systemd` exists in-container
as a real directory but has no `system` child, so `sd_booted()` is false and
anything gating on "is systemd available here?" (`openclaw doctor`,
`gateway status --deep`, `systemctl is-system-running`) concludes there is none.
Symlinking `/run/host/run/systemd/system` in as `/run/systemd/system` flips
`is-system-running` from `offline` to `running`.

**The `/run/dbus/system_bus_socket` half of that wiki recipe is deliberately
omitted.** It grants *system* scope, which would let anything in this box drive
host system services via `sudo systemctl`. User scope is all OpenClaw needs.
Lingering — the one thing that genuinely wants the system bus — is detected
instead by reading `/run/host/var/lib/systemd/linger/$USER`, a plain file check,
and the user is told to run `loginctl enable-linger` on the host themselves.

## Pitfalls and notes

1. **An exported `node` from *any* box shadows every other box's node.**
   `~/.local/bin` is shared `$HOME` and sorts before `/usr/bin` on PATH, so
   `~/.local/bin/node` — here a `distrobox-export --bin` of **dev-toolbox-box**'s
   Node 22 — wins over this container's Node 24 for every `#!/usr/bin/env node`
   shebang. The failure is baffling rather than obvious: the export wrapper
   re-enters *dev-toolbox-box* and runs node there, so you get
   `Error: Cannot find module '/usr/bin/openclaw-bin'` — a path that exists only
   in the openclaw container — instead of a version complaint. Fix: never rely on
   `env node`; `openclaw-bin` names `/usr/bin/node` explicitly. OpenClaw's
   launcher respawns itself via `process.execPath`, so pinning it once carries to
   its children. Any future Node app in this repo has the same exposure.
2. `/run` is a tmpfs recreated on every container start, so the systemd symlink
   cannot be baked into the image — each wrapper calls `ensure_systemd_bridge` on
   the way in. It is idempotent and non-fatal.
3. **`openclaw onboard` can offer to install a systemd user service.** Accepting
   it writes a unit into the shared `~/.config/systemd/user/` whose `ExecStart`
   names container-only paths, so the host manager — which is the one that picks
   it up — can never start it. The `openclaw` wrapper appends a skip flag to
   `onboard`/`setup` unless the caller passed a daemon flag themselves. The flag
   name is **resolved at image build time** into `/usr/lib/openclaw/daemon-skip-flag`,
   because OpenClaw's own docs use both `--skip-daemon` (wizard-cli-automation)
   and `--no-install-daemon` (install/docker); 2026.9.3 accepts `--skip-daemon`.
   An empty file means neither was recognised and nothing is injected.
4. **The gateway defaults to `0.0.0.0` inside a container.** OpenClaw prints it
   plainly: *"Container environment detected — the gateway defaults to bind=auto
   (0.0.0.0) for port-forwarding compatibility."* Distrobox boxes use
   `--network host`, so there is no port forward to serve and that default would
   publish the agent to the LAN. `openclaw-gateway` pins `--bind loopback`.
   Note the guard that catches this is *auth-dependent*: OpenClaw refuses `auto`
   only while auth is off, so a freshly onboarded install (which has a gateway
   token) would bind `0.0.0.0` silently. Verified: with the pin, `ss -ltnp` shows
   `127.0.0.1` + `[::1]` only, and both LAN addresses refuse the connection.
5. **npm skips four packages' install scripts** and warns loudly
   (`@google/genai`, `koffi`, `tree-sitter-bash`, `protobufjs`). Harmless on
   linux-x64 and intentionally not worked around: `koffi`'s native binary arrives
   via the hoisted optional dep `@koromix/koffi-linux-x64` (verified —
   `require("koffi")` loads), `tree-sitter-bash` ships `prebuilds/linux-x64`, and
   the other two scripts are an `echo` and a message. Pinning npm's
   `--allow-scripts` to that package list would just rot with each release.
   `--allow-scripts=true` does **not** work — npm still skips and warns.
6. **The PID namespace is shared with the host.** `pkill -f 'gateway run'` from
   inside the box matched the outer `distrobox enter ... gateway run ...` command
   line and killed the calling session instead (exit 144). Kill by PID when
   testing, or use a pattern that cannot match your own argv.
7. `OPENCLAW_STATE_DIR`/`OPENCLAW_CONFIG_PATH` do **not** fully isolate a run —
   a smoke test with both set still created `~/.openclaw/state/openclaw.sqlite`.
   Use `--profile <name>` if you need real isolation.
8. `openclaw update` rewrites the npm install inside the container and would
   restore npm's `env node` shim over `openclaw-bin`. Update by re-running
   `tools setup openclaw` instead.
